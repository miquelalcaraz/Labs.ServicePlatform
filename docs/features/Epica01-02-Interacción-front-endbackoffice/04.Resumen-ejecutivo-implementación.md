# Resumen Ejecutivo — Implementación Épica 01-02: Interacción Front-End Backoffice

## 1. Objetivo

Implementar la interacción completa entre el BackOffice (front-end Blazor) y la API de Accounts para la gestión del proceso de Customer Onboarding, cubriendo:

1. **Backend (Fases 0–6):** Read model con DTOs, display helpers, query handlers, 5 endpoints REST, retry command/handler, migración EF, y tests funcionales.
2. **Frontend (Fase 7):** 4 páginas Blazor con componentes Radzen, typed HttpClient con service discovery de Aspire, navegación lateral, y polling adaptativo.
3. **Autorización:** Políticas por rol en cada endpoint según la authorization matrix del documento de diseño.

Todo construido sobre la base de las Épicas 01-00 y 01-01, sin romper contratos existentes.

| Propiedad | Tipo | Propósito |
|-----------|------|-----------|
| `CompanyLegalName` | `string?` | Nombre legal de la empresa (capturado al iniciar) |

#### Polling adaptativo

| Aspecto | Detalle |
|---------|---------|
| **Mecanismo** | `Task.Delay` loop con `CancellationTokenSource` |
| **Start** | En `OnInitializedAsync()` y tras cada Refresh/Retry |
| **Intervalo activo** | 5 segundos (status `InProgress`) |
| **Intervalo waiting** | 25 segundos (status `WaitingFor*`) |
| **Stop** | Status terminal (`Completed`, `Failed`) o navegación fuera de la página |
| **UI update** | `await InvokeAsync(StateHasChanged)` (thread-safe para SignalR) |
| **Cleanup** | `IAsyncDisposable` cancela el token al disponer el componente |

**Criterio:** `Task.Delay` sobre `PeriodicTimer` porque es más simple para polling HTTP (no requiere precisión de timer), maneja cancellation naturalmente, y el intervalo adaptativo se resuelve releyendo el status tras cada poll.

## 4. Autorización

### Políticas registradas

3 políticas definidas en `BackOfficeAuthorizationPolicies`:

| Política | Roles permitidos |
|----------|-----------------|
| `BackOffice.Onboarding.Write` | ProjectManager, BusinessAdmin, PlatformAdmin |
| `BackOffice.Onboarding.Read` | ProjectManager, BusinessAdmin, SupportAgent, PlatformAdmin |
| `BackOffice.Onboarding.Retry` | ProjectManager, SupportAgent, PlatformAdmin |

### Aplicación por endpoint

| Endpoint | Política |
|----------|----------|
| `POST /` (Start) | `OnboardingWrite` |
| `GET /{id}` (Detail) | `OnboardingRead` |
| `GET /` (List) | `OnboardingRead` |
| `POST /{id}/retry` (Retry) | `OnboardingRetry` |
| `GET /{id}/result` (Result) | `OnboardingRead` |

**Criterio:** La authorization matrix sigue exactamente el documento de diseño `03.Refinamiento API de Backoffice.md § 11`. Cada endpoint tiene `.RequireAuthorization(policy)` individual en lugar de un único `RequireAuthorization()` en el group, permitiendo granularidad por operación.

### Registro en Program.cs

```csharp
builder.Services.AddAuthorizationBuilder()
    .AddPolicy(BackOfficeAuthorizationPolicies.OnboardingWrite, policy =>
        policy.RequireRole(Roles.ProjectManager, Roles.BusinessAdmin, Roles.PlatformAdmin))
    .AddPolicy(BackOfficeAuthorizationPolicies.OnboardingRead, policy =>
        policy.RequireRole(Roles.ProjectManager, Roles.BusinessAdmin, Roles.SupportAgent, Roles.PlatformAdmin))
    .AddPolicy(BackOfficeAuthorizationPolicies.OnboardingRetry, policy =>
        policy.RequireRole(Roles.ProjectManager, Roles.SupportAgent, Roles.PlatformAdmin));
```

### Fix en tests funcionales

Tras añadir las políticas, los 14 tests de backoffice fallaron con `401 Unauthorized`. Se corrigió `AutoAuthorizeMiddleware` añadiendo claims de rol:

```csharp
identity.AddClaim(new Claim(ClaimTypes.Role, "PlatformAdmin"));
identity.AddClaim(new Claim("role", "PlatformAdmin"));
```

Se usan **ambos** claim types porque el sistema de Identity emite `"role"` (claim type corto) mientras que `RequireRole()` de ASP.NET Core busca `ClaimTypes.Role` por defecto. Incluir ambos garantiza compatibilidad.

## 7. Decisiones de arquitectura y criterios

### 7.1 Display helpers en el server (no en Blazor)

**Decisión:** La lógica de `ProgressPercent`, `StatusDisplayName`, `StepsList`, y `Actions` se calcula en `OnboardingDisplayHelpers` (server) y se envía como parte del DTO.

**Criterio:**
- Cualquier cliente (Blazor, mobile, third-party) recibe la misma presentación
- Un solo lugar donde mantener las reglas de display
- El front-end es un "thin client" que renderiza lo que recibe

**Trade-off:** El DTO es más grande, pero evita duplicar lógica de negocio en cada cliente.

### 7.2 Snapshot properties vs JOINs

**Decisión:** `OnboardingProcess` almacena `CompanyLegalName`, `SubscriptionPlanCode`, `AdminEmail` como propiedades snapshot.

**Criterio:**
- El listado necesita datos de resumen sin hacer JOINs costosos
- El onboarding es un proceso de larga duración — los valores capturados al inicio son los relevantes (no los actuales de la empresa)
- Consistencia con el patrón Event Sourcing-lite: el snapshot es la "foto" del momento

**Trade-off:** Duplicación de datos, pero es aceptable porque son inmutables en el contexto del proceso.

### 7.3 DTOs duplicados entre server y client

**Decisión:** Los DTOs del BackOffice WebApp (`Models/OnboardingModels.cs`) son copias independientes de los DTOs del server.

**Criterio:**
- El WebApp es un cliente HTTP que podría vivir en un repositorio separado
- No se comparte un paquete NuGet de contratos (aún) porque el API contract no está estabilizado
- Independencia de deployment entre WebApp y API

**Trade-off:** Si cambia el contrato del API, hay que actualizar ambos lados manualmente. Futuro: considerar un paquete `Qlt.Services.Accounts.Contracts` cuando los contratos se estabilicen.

### 7.4 Polling con Task.Delay vs SignalR/Server-Sent Events

**Decisión:** Polling HTTP periódico con `Task.Delay` loop en el componente Blazor.

**Criterio:**
- El onboarding es un proceso de minutos/horas — polling cada 5-25s es suficiente
- No requiere infraestructura adicional (hub SignalR, SSE endpoint)
- Implementación simple y predecible con cancellation token
- Intervalo adaptativo reduce carga en estados de espera

**Trade-off:** No es real-time. Latencia máxima = intervalo de polling. Aceptable para el caso de uso.

### 7.5 Autorización per-endpoint vs per-group

**Decisión:** `.RequireAuthorization(policy)` en cada endpoint individual, no en el `MapGroup`.

**Criterio:**
- La authorization matrix del diseño define permisos distintos por operación (Write vs Read vs Retry)
- Granularidad permite que un `SupportAgent` lea pero no cree
- El group ya tiene `.RequireAuthorization()` genérico (authenticated), las políticas agregan role-checks

### 7.6 ApiResult<T> vs excepciones

**Decisión:** `ApiResult<T>` como envelope de resultado en `OnboardingApiService`.

**Criterio:**
- Las respuestas HTTP 4xx no son excepciones (son flujo normal: not found, bad request)
- El componente Blazor puede branching limpio: `if (result.IsSuccess)` vs verificar StatusCode
- Consistente con el `Result<T>` pattern usado en todo el backend

### 7.7 PlatformAdmin como rol de test

**Decisión:** El `AutoAuthorizeMiddleware` de tests funcionales asigna el rol `PlatformAdmin`.

**Criterio:**
- `PlatformAdmin` tiene acceso a todos los endpoints (read + write + retry)
- Un solo rol cubre todos los escenarios de test sin necesidad de fixtures por rol
- Claims en ambos formatos (`ClaimTypes.Role` y `"role"`) por compatibilidad

## 8. Puntos a mejorar o revisar

### 🔴 Prioridad alta

| Item | Detalle | Razón |
|------|---------|-------|
| **Token propagation en modo interactivo** | `AddAuthToken()` usa `IHttpContextAccessor` que solo funciona durante SSR. En modo interactivo (SignalR), el `HttpContext` puede ser null y el token no se propaga. | Las páginas Blazor usan `@attribute [Authorize]` pero las llamadas HTTP al API podrían fallar sin token en escenarios interactivos reales. Requiere implementar `CircuitHandler` o `AuthenticationStateProvider` custom para extraer y cachear el token. |
| **Tests funcionales por rol** | Solo se testea con `PlatformAdmin`. No hay tests que verifiquen que `SupportAgent` NO puede hacer POST (start). | La matrix de autorización no está validada negativamente. Añadir tests con diferentes roles para verificar 403 Forbidden. |
| **Validación del request body** | `StartOnboardingProcessRequest` no tiene `FluentValidation` — la validación es solo DataAnnotations en el client Blazor. | Un cliente directo al API (Postman, otro servicio) podría enviar datos inválidos sin validación server-side. Añadir `StartOnboardingProcessRequestValidator`. |

### 🟡 Prioridad media

| Item | Detalle | Razón |
|------|---------|-------|
| **Paginación server-side incompleta** | `RadzenDataGrid` hace paginación con `Page` event, pero no soporta sorting server-side (está deshabilitado: `AllowSorting="false"`). | El query handler ya soporta `sortBy` y `sortDirection`. Habilitar sorting server-side en el DataGrid. |
| **Error contract inconsistente** | Los endpoints devuelven `BadRequest<string>` (plain text) en lugar del error contract definido en el doc (`{ code, message, traceId, errors }`). | Alinear con el error contract del doc `03.Refinamiento API de Backoffice.md § 3`. Usar `ProblemDetails` o el error DTO definido. |
| **Retry reason en el UI** | El formulario de retry no pide razón al usuario. `RetryOnboardingRequest.Reason` existe pero no se usa en la UI. | Añadir un modal de confirmación con campo "Reason" antes del retry. |
| **Accesibilidad** | Las páginas usan componentes Radzen con `aria-*` básico pero no se han verificado con screen reader. | Revisar con herramientas de accesibilidad (Lighthouse, NVDA). |
| **Shared contracts package** | DTOs duplicados entre server y client. | Cuando la API se estabilice, extraer `Qlt.Services.Accounts.Contracts` como paquete NuGet compartido. |

### 🟢 Prioridad baja

| Item | Detalle | Razón |
|------|---------|-------|
| **Notificación real-time al completar** | El polling detecta `Completed` con latencia de hasta 25s. | Considerar SignalR hub para notificación instantánea cuando el uso lo justifique. |
| **Caché de listado** | Cada cambio de página/filtro hace una llamada HTTP. | Implementar output cache o in-memory cache con TTL corto para el listado. |
| **i18n** | Display names hardcoded en inglés ("In Progress", "Waiting for Activation"). | Cuando se implemente internacionalización, mover a resource files. |
| **Idempotency-Replayed header** | No implementado — documentado como "wait for real use case" (YAGNI). | Implementar solo si un cliente necesita distinguir respuestas originales de replay. |
| **Steps 7-9 del onboarding** | ActivationRequested → ActivationDelivered → UserActivated no implementados. | Requiere integración con Notifications service (Épica futura). |

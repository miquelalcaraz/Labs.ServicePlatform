# 1. Objetivos de la API de Backoffice

Esta API debe permitir a usuarios internos:

- iniciar un onboarding
- consultar su estado
- listar onboardings
- reintentar procesos fallidos
- obtener el resultado final del alta

Y debe hacerlo respetando que:

- el onboarding es un **long-running process**
- parte del flujo es asíncrono
- `Account` es el owner del proceso
- `Identity` y `Notifications` participan indirectamente

```
/api/backoffice/onboarding-processes
```

## Media type


OIDC/OAuth2 access token emitido por `Identity`.

Acceso restringido a internal users con roles de plataforma apropiados.

## Time format

Todos los timestamps en:

```
UTC ISO-8601
```


- `code`: código funcional o técnico controlado

# 5. Endpoint — Start onboarding

## Purpose

Crear un nuevo `OnboardingProcess` y arrancar el alta del customer.

## Endpoint

```
POST /api/backoffice/onboarding-processes
```

## Authorization

Permitido para:

- `ProjectManager`
- `BusinessAdmin`
- opcionalmente `PlatformAdmin`

---

## Request body

```
{
  "company": {
    "legalName":"Acme Industrial Supplies Ltd",
    "tradeName":"Acme Supplies",
    "taxId":"B12345678",
    "countryCode":"ES"
  },
  "subscription": {
    "subscriptionPlanCode":"B2B_PRO"
  },
  "adminUser": {
    "firstName":"Laura",
    "lastName":"Martinez",
    "email":"laura.martinez@acme.com",
    "preferredLanguage":"en"
  }
}
```

---

## Request contract

### `company`

- `legalName: string` required, max 250
- `tradeName: string?` optional, max 250
- `taxId: string?` optional, max 50
- `countryCode: string?` optional, max 10

### `subscription`

- `subscriptionPlanCode: string` required, max 100

### `adminUser`

- `firstName: string` required, max 100
- `lastName: string` required, max 150
- `email: string` required, valid email format
- `preferredLanguage: string?` optional, max 10

---

## Success response

### Recommended status

```
202 Accepted
```

### Body

```
{
  "onboardingProcessId":"3d2898f1-1e6a-4a2b-b9f5-514e1b7d8c61",
  "subscriptionId":"6ec8f84e-5d54-446c-a2a7-63e3af8c57e2",

    "result":"/api/backoffice/onboarding-processes/3d2898f1-1e6a-4a2b-b9f5-514e1b7d8c61/result"
```

# 12. Idempotency behavior

## Start onboarding

`POST /onboarding-processes` debería soportar `Idempotency-Key`.

### Expected behavior

Si llega la misma request con la misma key:

- no crear un nuevo onboarding
- devolver la misma respuesta lógica del primero

## Retry onboarding

`POST /{id}/retry` también debería soportarlo.

### Expected behavior

Si el mismo retry se envía dos veces con la misma key:

- solo se procesa una vez

# 14. Front-end polling strategy aligned to these APIs

## After `POST /onboarding-processes`

Redirigir a:

```
GET /api/backoffice/onboarding-processes/{id}
```

## Poll every

- 3–5 segundos en estados activos:
    - `InProgress`
    - `WaitingForExternalProvisioning`
    - `WaitingForActivationDelivery`
- 20–30 segundos o manual en:
    - `WaitingForUserActivation`

## Stop polling on

- `Completed`
- `Failed`

# 16. Recomendación importante de diseño

No devolvería directamente los aggregates `Subscription`, `Tenant`, `Company`, `OnboardingProcess` serializados tal cual.

Mejor exponer:

- **command DTOs**
- **UI read models**
- **responses orientadas a caso de uso**

Eso os da libertad para evolucionar el dominio sin romper el front.

# 18. Recomendaciones de implementación

## HTTP semantics

- `202 Accepted` para operaciones que disparan proceso asíncrono
- `200 OK` para lecturas
- `400` para validación
- `404` para inexistencia
- `409` para conflicto o estado inválido
- `401/403` para auth/authz

## Backoffice read model

Muy recomendable que `GET /{id}` salga de una proyección optimizada para UI y no de reconstrucción en caliente demasiado compleja.

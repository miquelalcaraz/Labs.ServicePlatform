## 1. Retry Semantics — State Machine Consistency

### Problem

After calling `Retry()`, the aggregate status resets to `InProgress`. However, `MarkAdminUserProvisioned()` requires `WaitingForExternalProvisioning` as a precondition. This created an unreachable state: Identity dispatches `ExternalUserProvisionedIntegrationEvent`, but the event handler cannot advance the process because the status guard fails.

### Solution

Added `RestartAdminProvisioning()` as an explicit bridge transition:

```
Retry() → InProgress + AdminProvisioningRequested step
RestartAdminProvisioning() → WaitingForExternalProvisioning + AdminProvisioningRequested step
                                      ↓
MarkAdminUserProvisioned() → InProgress + AdminUserProvisioned step
```

`RetryOnboardingProcessCommandHandler` calls `Retry()` followed by `RestartAdminProvisioning()` atomically, restoring the exact precondition expected by the integration event handler.

### Files changed

| File | Change |
|------|--------|
| `OnboardingProcess.cs` | Added `RestartAdminProvisioning()` with `EnsureStatus(InProgress)` + `EnsureStep(AdminProvisioningRequested)` guards |
| `RetryOnboardingProcessCommandHandler.cs` | Added `onboarding.RestartAdminProvisioning()` call after `Retry()` |
| `OnboardingProcessTests.cs` | 6 new tests covering happy path, wrong status, and wrong step guards |

## 2. Token Propagation in Blazor Interactive Server Mode

### Problem

`HttpContext` is not available during the SignalR circuit phase in Blazor Interactive Server. `IHttpContextAccessor` returns `null` after the initial SSR prerender, breaking any service that reads the authentication token (Bearer) from the HTTP request — specifically the typed `HttpClient` used to call the Accounts API.

### Solution

Implemented a scoped `TokenProvider` pattern:

1. During SSR prerender (`OnInitializedAsync` with `!InteractiveRenderMode`), the token is read from `HttpContext` and stored in a scoped `TokenProvider`.
2. The `DelegatingHandler` on the typed client reads from `TokenProvider` instead of `IHttpContextAccessor`.
3. The scoped lifetime ensures the token survives the full Blazor circuit within a single user session.

### Files changed

| File | Change |
|------|--------|
| `TokenProvider.cs` | New scoped service holding `AccessToken` |
| `BackOfficeAuthorizationHandler.cs` | Reads token from `TokenProvider` instead of `IHttpContextAccessor` |
| `ApplicationAuthenticationStateProvider.cs` | Populates `TokenProvider` during SSR prerender |
| `Program.cs` (BackOfficeApp) | Registered `TokenProvider` as scoped |

## 3. Server-Side Validation of StartOnboarding

### Problem

Two server-side validation bypasses were identified in `StartCustomerOnboardingCommand`:

1. **`TaxNumberType` silent coercion:** The DTO property was non-nullable (`TaxNumberType TaxNumberType`), causing JSON deserialization to silently coerce any missing or invalid value to `0` (enum default), bypassing the `[Required]` validation on the front-end form.
2. **`TradeName` fallback:** The API endpoint applied `LegalName` as a fallback for missing `TradeName` before reaching the validator, making the `[Required]` annotation on the Blazor form decorative rather than enforced.

### Solution

- Made `TaxNumberType` nullable in the DTO (`TaxNumberType? TaxNumberType`). The API endpoint explicitly maps `null` to a safe default (`TaxNumberType.Vat`), and the validator rejects empty or unknown enum values.
- Removed the `TradeName` fallback from the endpoint; `TradeName` is now passed as-is to the command, and the validator enforces its presence.
- Added matching `[Required]` attributes on the Blazor `EditForm` model to align client-side and server-side constraints.

### Files changed

| File | Change |
|------|--------|
| `BackOfficeOnboardingApi.cs` | Removed `TradeName` fallback; `TaxNumberType` null defaults to `Vat` |
| `StartCustomerOnboardingCommandValidator.cs` | Added `TaxNumberType` and `TradeName` validation rules |
| `OnboardingRequestModels.cs` (BackOfficeApp) | `TaxNumberType` nullable; `TradeName` marked `[Required]` |

## 4. Homogeneous Error Contract

### Problem

The API surface returned inconsistent error shapes depending on the code path:

- `ExceptionHandlingMiddleware` produced RFC 7807 ProblemDetails (`type`, `title`, `status`).
- Endpoints returned `BadRequest<string>` (plain text), `NotFound` (no body), or `ValidationProblem` (different schema).
- Retry-not-allowed was mapped to `400 Bad Request` instead of `409 Conflict`, which broke idempotency semantics (clients could not distinguish a business conflict from a request error).

### Solution

Introduced `ApiErrorResponse` as the single canonical error type across the entire API surface:

```json
{
  "code": "NotFound",
  "message": "Onboarding process with id '...' was not found.",
  "traceId": "...",
  "errors": { "field": ["message"] }
}
```

- `ExceptionHandlingMiddleware` now serializes `ApiErrorResponse` for both validation (400) and unexpected (500) errors.
- `ResultApiExtensions.ToHttpResult<T>()` returns `Results<Ok<T>, BadRequest<ApiErrorResponse>>`.
- All five `BackOfficeOnboardingApi` endpoints, `AccountsApi`, and `SubscriptionsApi` were updated to use `HttpContext` for `traceId` and typed result unions with `NotFound<ApiErrorResponse>`, `Conflict<ApiErrorResponse>`, and `BadRequest<ApiErrorResponse>`.
- `RetryNotAllowed` domain error correctly maps to `409 Conflict`.

### Files changed

| File | Change |
|------|--------|
| `ApiErrorResponse.cs` | New type in `Qlt.Platform`; static `From(Error, traceId?)` factory |
| `ExceptionHandlingMiddleware.cs` | Updated both handlers to produce `ApiErrorResponse` |
| `ResultApiExtensions.cs` | Return type changed to `Results<Ok<T>, BadRequest<ApiErrorResponse>>` |
| `BackOfficeOnboardingApi.cs` | All 5 endpoints updated; `RetryOnboarding` → `409 Conflict` |
| `AccountsApi.cs` | `NotFound<ApiErrorResponse>`, `BadRequest<ApiErrorResponse>` |
| `SubscriptionsApi.cs` | `BadRequest<ApiErrorResponse>` |
| `BackOfficeOnboardingApiTests.cs` | `RetryOnboarding_OnNonFailedProcess_ReturnsConflict` (was `ReturnsBadRequest`) |

## 5. Explicit "Done" Definition for Onboarding

### Problem

The state machine design specified a full activation flow (`ActivationRequested → ActivationDelivered → UserActivated → Completed`), but the implementation used a `Complete()` method documented as a "V1 convenience bypass" that closed the process directly after `AdminMembershipCreated`. This created a conceptual inconsistency: the domain model exposed methods and statuses for states that were never reachable at runtime.

### Root cause analysis

The activation flow requires two external integrations not yet built:
- A `Notifications` service to deliver the activation email and publish `ActivationDeliveredIntegrationEvent`.
- An `UserActivatedIntegrationEvent` from Identity triggered by the user clicking the activation link.

Rather than leaving unreachable code in the domain, the decision was to formalize V1's terminal state.

### Solution

The V1 terminal condition is: **the onboarding is done when the admin membership has been established**. All provisioned entities (Subscription, Tenant, Owner Company, Admin User, Admin Membership) exist and are operational.

Changes applied:

- **Removed** from `OnboardingStatus`: `WaitingForActivationDelivery`, `WaitingForUserActivation`.
- **Removed** from `OnboardingStep`: `ActivationRequested`, `ActivationDelivered`.
- **Removed** from `OnboardingProcess`: `ActivationDeliveredAtUtc`, `UserActivatedAtUtc` properties and `MarkActivationRequested()`, `MarkActivationDelivered()`, `MarkUserActivated()` methods.
- **Rewrote** `Complete()` with proper domain guards — no longer a bypass:
  ```csharp
  public void Complete()
  {
      EnsureStatus(OnboardingStatus.InProgress);
      EnsureStep(OnboardingStep.AdminMembershipCreated);
      Status = OnboardingStatus.Completed;
      CurrentStep = OnboardingStep.Completed;
      CompletedAtUtc = DateTimeOffset.UtcNow;
  }
  ```
- **`/result` endpoint** documented via `.WithSummary()` / `.WithDescription()`: returns Subscription, Tenant, Owner Company, Admin User, and Admin Membership once `Status = Completed`.
- **Progress percentages** redistributed across the 6 remaining intermediate steps: `0 / 15 / 30 / 45 / 55 / 70 / 85 / 100`.
- **UX polling** updated: only `InProgress` and `WaitingForExternalProvisioning` trigger auto-refresh; `WaitingForExternalProvisioning` uses a 10s interval.

## 6. Role-Based Authorization Tests (positive + negative)

### Problem

The BackOffice onboarding API exposed three authorization policies (`OnboardingWrite`, `OnboardingRead`, `OnboardingRetry`) but had no automated test coverage validating the authorization matrix. An incorrect role being granted — or a missing role restriction — would only be discovered in production.

### Solution

Added a dedicated functional test class `BackOfficeOnboardingAuthorizationTests` that validates every cell of the authorization matrix using a custom `X-Test-Role` HTTP header injected by a test-only `AutoAuthorizeMiddleware`.

**Authorization matrix tested:**

| Policy | ProjectManager | BusinessAdmin | SupportAgent | PlatformAdmin |
|--------|:-:|:-:|:-:|:-:|
| `OnboardingWrite` (Start) | ✅ 202 | ✅ 202 | ❌ 403 | ✅ 202 |
| `OnboardingRead` (List/Detail/Result) | ✅ 200/404 | ✅ 200/404 | ✅ 200/404 | ✅ 200/404 |
| `OnboardingRetry` (Retry) | ✅ 404 | ❌ 403 | ✅ 404 | ✅ 404 |

Root cause of a discovered `401 → 403` regression: `AutoAuthorizeMiddleware` was calling `httpContext.User.AddIdentity(identity)` which appended to the default unauthenticated identity (index 0 remained anonymous), causing `AuthenticateResult` to fail before the authorization policy could evaluate the role claim. Fixed by replacing the principal entirely: `httpContext.User = new ClaimsPrincipal(identity)`.

### Files changed

| File | Change |
|------|--------|
| `BackOfficeOnboardingAuthorizationTests.cs` | New — 12 tests (2 negative × 403, 10 positive × role-specific expected status) |
| `AutoAuthorizeMiddleware.cs` | Fixed: `httpContext.User = new ClaimsPrincipal(identity)` (was `AddIdentity`) |

## 9. Minimum Consistent Observability

### Problem

The onboarding process is a long-running, cross-service flow critical for production support. Three observability gaps were identified:

1. **Missing `CorrelationId` in log scopes** — command handlers logged aggregate IDs but not the `CorrelationId` (the original `x-requestid` stored on `OnboardingProcess`), making it impossible to correlate logs from the API layer, the command handler, and the integration event handler across a single onboarding lifecycle.
2. **`LastError` always null in production** — `OnboardingProcess.Fail()` existed in the domain but was never called anywhere in the application code. If Identity's event handler encountered a domain exception, the process was left in an undefined state and `LastError` / `LastErrorCode` returned by the query layer were always `null`.
3. **Silent failure paths in the API layer** — `RetryOnboarding` returned `NotFound` and `Conflict` responses without any log entry, and `StartOnboarding`'s failure log omitted the error code and message.

### Solution

**`ExternalUserProvisionedIntegrationEventHandler`** (highest priority):
- Added a **completed guard**: if `onboarding.Status == Completed`, log and return — prevents infinite NACK-retry loop on duplicate message delivery.
- Wrapped domain operations in `try-catch (AccountDomainException)`: calls `onboarding.Fail("IntegrationEventProcessingError", ex.Message)` and saves — the process moves to `Failed` status, `LastError` is populated, and the BackOffice operator can trigger a manual retry. Does not rethrow (ACK), preserving the message from the dead-letter queue.
- All domain operations wrapped in `BeginScope(CorrelationId = onboarding.CorrelationId)`.

**`StartCustomerOnboardingCommandHandler`**: entire `Handle()` body wrapped in `BeginScope(CorrelationId = message.RequestId)`.

**`RetryOnboardingProcessCommandHandler`**:
- Added `LogWarning` before each early-return `Result.Failure` (not-found, wrong-status).
- Retry logic wrapped in `BeginScope(CorrelationId = onboarding.CorrelationId)` after the aggregate is loaded.

**`BackOfficeOnboardingApi`**:
- `StartOnboarding` failure log enriched with `ErrorCode` and `ErrorMessage`.
- `RetryOnboarding` failure branches each emit a targeted `LogWarning` (NotFound / RetryNotAllowed / generic).

### Observability state after fix

| Point | CorrelationId in scope | traceId in errors | Log on failure | `lastError` populated |
|-------|:-:|:-:|:-:|:-:|
| API — Start | ✅ | ✅ | ✅ improved | — |
| Handler — Start | ✅ new | — | ✅ | — |
| API — Retry | ✅ | ✅ | ✅ new | — |
| Handler — Retry | ✅ new | — | ✅ new | — |
| Integration event handler | ✅ new | — | ✅ new | ✅ **unblocked** |

### Files changed

| File | Change |
|------|--------|
| `ExternalUserProvisionedIntegrationEventHandler.cs` | Completed guard; `AccountDomainException` catch → `Fail()` + save; `BeginScope(CorrelationId)` |
| `StartCustomerOnboardingCommandHandler.cs` | `Handle()` body wrapped in `BeginScope(CorrelationId = message.RequestId)` |

## 11. Unused Integration Event Cleanup

### Problem

Audit of the integration event surface revealed two categories of "zombie events" — events that generate outbox writes, consume message bus capacity, and add architectural noise without delivering business value:

1. **`SubscriptionCreatedIntegrationEvent`** — published by `SubscriptionCreatedDomainEventHandler` on every subscription creation, but consumed by no service in the solution. Identity does not subscribe to it; Notifications does not subscribe to it.
2. **`CompanyCreatedIntegrationEventHandler` in Identity** — subscribed to `CompanyCreatedIntegrationEvent` but contained only a `LogInformation` call and returned `Task.CompletedTask`. Its own XML summary read *"Legacy handler — tenant and user creation moved to dedicated handlers."* The event itself remains active and valuable (Notifications uses it to send welcome emails).

### Complete event registry after cleanup

| Event | Publisher | Consumer(s) | Status |
|-------|-----------|-------------|--------|
| `CustomerAdminProvisioningRequestedIntegrationEvent` | Accounts | Identity ✅ (provisions admin user) | ✅ Active — critical |

| `CompanyCreatedIntegrationEvent` | Accounts | Notifications ✅ (welcome email + sales) | ✅ Active |

## Future Work

The activation flow remains designed at the domain level and can be reintroduced when the `Notifications` service integration is available:

1. After `AdminMembershipCreated`, publish `ActivationEmailRequestedIntegrationEvent` → Notifications service.
2. Notifications delivers the email and publishes `ActivationDeliveredIntegrationEvent` → Accounts handler calls `MarkActivationDelivered()`.
3. User clicks the activation link → Identity publishes `UserActivatedIntegrationEvent` → Accounts handler calls `MarkUserActivated()` (which sets `Status = Completed` directly — `Complete()` becomes redundant).

At that point, `Complete()` can be removed and the three `Mark*()` methods reintroduced.

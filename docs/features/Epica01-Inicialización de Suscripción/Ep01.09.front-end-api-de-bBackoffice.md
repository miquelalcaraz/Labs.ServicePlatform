## 8.1 Start onboarding

### Endpoint

`POST /api/backoffice/onboarding-processes`

### Request

```
{
  "company": {
    "legalName":"Acme Industrial Supplies Ltd",
    "tradeName":"Acme Supplies",
    "taxId":"B12345678",
    "countryCode":"ES"
  },
  "subscription": {
    "subscriptionPlanCode":"B2B_PRO"
  },
  "adminUser": {
    "firstName":"Laura",
    "lastName":"Martinez",
    "email":"laura.martinez@acme.com",
    "preferredLanguage":"en"
  }
}
```

### Response recomendada

`202 Accepted`

```
{
  "onboardingProcessId":"3d2898f1-1e6a-4a2b-b9f5-514e1b7d8c61",
  "subscriptionId":"6ec8f84e-5d54-446c-a2a7-63e3af8c57e2",
  "status":"InProgress",
  "currentStep":"SubscriptionCreated",
  "links": {
    "self":"/api/backoffice/onboarding-processes/3d2898f1-1e6a-4a2b-b9f5-514e1b7d8c61"
  }
}
```

## Por qué `202 Accepted`

Porque semánticamente el proceso completo no termina dentro de la request.

Aunque parte del trabajo se haga sincrónicamente, el resultado de negocio final es asíncrono.

## 8.3 List onboarding processes

### Endpoint

`GET /api/backoffice/onboarding-processes`

### Query params recomendados

- `status`
- `companyName`
- `adminEmail`
- `subscriptionId`
- `page`
- `pageSize`
- `sort`

### Ejemplo

`GET /api/backoffice/onboarding-processes?status=Failed&page=1&pageSize=20`

### Respuesta

Lista resumida orientada a grid.

---

## 8.4 Retry onboarding

### Endpoint

`POST /api/backoffice/onboarding-processes/{onboardingProcessId}/retry`

### Request

```
{
  "reason":"Retry requested by Project Manager after correcting admin email"
}
```

### Response

`202 Accepted`

```
{
  "onboardingProcessId":"3d2898f1-1e6a-4a2b-b9f5-514e1b7d8c61",
  "status":"InProgress",
  "currentStep":"AdminProvisioningRequested"
}
```

## Regla importante

El retry debe ser **explícito**.

No recomiendo que el front-end vuelva a enviar el alta completa como forma de retry.

# 9. Validación y errores en la UX

Aquí conviene separar dos tipos.

## A. Validation errors síncronos

Errores detectados antes de iniciar onboarding.

Ejemplos:

- `Company Legal Name` missing
- invalid email
- invalid `SubscriptionPlanCode`

### Respuesta recomendada (Utilizar predefinida en Qlt.Platform “Arquitectura Base”)

`400 Bad Request`

```
{
  "code":"ValidationError",
  "message":"One or more validation errors occurred.",
  "errors": {
    "company.legalName": ["Legal name is required."],
    "adminUser.email": ["Email format is invalid."]
  }
}
```

### UX

Mostrar errores inline por campo.

---

## B. Process errors asíncronos

Errores que ocurren una vez el onboarding ya arrancó.

Ejemplos:

- user provisioning conflict
- activation email failed
- duplicate email in identity

### UX

No deben volver al formulario como si fuera un validation error clásico.

Deben aparecer en la pantalla de detalle del onboarding como:

- `Status = Failed`
- `CurrentStep = ...`
- `LastErrorCode`
- `LastErrorMessage`
- acción `Retry`

# 10. Modelo de estado en el front-end

La SPA debería tener dos niveles de estado:

## A. Command state

Para acciones inmediatas:

- submitting
- success
- error

Ejemplo: submit del formulario

## B. Process state

Para el workflow largo:

- `status`
- `currentStep`
- timeline de pasos
- retry available
- resulting ids

## Recomendación

No mezclar ambos estados en un único store ambiguo.

---

# 11. Representación recomendada del estado en UI

## Process badge

- `Draft`
- `In Progress`
- `Waiting for Identity`
- `Waiting for Activation Delivery`
- `Waiting for User Activation`
- `Completed`
- `Failed`

## Step tracker

Un stepper vertical o timeline, mejor que tabs.

## Mensajes recomendados

### `WaitingForExternalProvisioning`

“Waiting for Identity service to provision the admin user.”

### `WaitingForActivationDelivery`

“Admin user created. Waiting for activation email delivery.”

### `WaitingForUserActivation`

“Activation email delivered. Waiting for the customer admin to activate the account.”

### `Failed`

“Onboarding failed during admin provisioning.”

Eso mejora mucho la comprensión operativa.

# 12. Seguridad y autorización en front-end

## Acceso al Backoffice

Solo internal users autenticados en `Identity`.

## Autorización mínima sugerida

### Puede iniciar onboarding

- `ProjectManager`
- quizá `BusinessAdmin`

### Puede ver onboarding

- `ProjectManager`
- `SupportAgent`
- `BusinessAdmin`
- `PlatformAdmin`

### Puede reintentar onboarding

- `ProjectManager`
- `SupportAgent`
- `PlatformAdmin`

## Recomendación

Que la UI oculte acciones no permitidas, pero la autorización real debe estar en backend.

# 13. Qué no debería hacer el front-end

No debería:

- llamar directamente a `Identity` para provisionar el usuario del customer
- llamar directamente a `Notifications`
- inferir estados complejos a partir de varios endpoints disjuntos
- decidir por su cuenta que un onboarding está “completado”
- volver a disparar “create onboarding” si el usuario no ve progreso

# 14. Estrategia de idempotencia en UI

<aside>
💡

Utilizar predefinida en Qlt.Platform “Arquitectura Base”.

</aside>

## En `Start Onboarding`

Proteger contra doble click o reenvío accidental.

### Recomendación

- deshabilitar el botón durante submit
- enviar un `x-requestid` header

Ejemplo:

`x-requestid: 8f3a5f14-4dc7-4f1f-b71f-d2bb8fd46e13`

## En `Retry`

Igual:

- botón deshabilitado mientras se procesa
- x-requestid por operación

# 15. Recomendación sobre composición de APIs

## Mejor opción para el backoffice

Tener endpoints que ya devuelvan **view models orientados a la UI**, no solo aggregates puros.

Por ejemplo:

- `GET /onboarding-processes/{id}` debería devolver:
    - estado global
    - steps
    - acciones disponibles
    - resumen customer

No limitarse a exponer la tabla `OnboardingProcesses` sin más.

# 17. Diseño de navegación recomendado

## Happy path

`Onboarding List`

→ `Start Onboarding`

→ submit

→ redirect a `Onboarding Detail`

→ si completed, botón `Open Customer`

## Failure path

`Onboarding Detail`

→ estado `Failed`

→ revisar error

→ `Retry`

# 18. Recomendación sobre queries de lectura

Aquí veo mucho valor en separar:

- **command model** para crear/reintentar
- **read model** optimizado para UI

Incluso aunque todo viva dentro de `Account`, el endpoint de lectura debería ser una proyección pensada para backoffice.

# 20. Propuesta final de implementación v1

## Front-end

- SPA de backoffice
- autenticación OIDC con `Identity`
- polling para onboarding status
- stepper/timeline para proceso
- acciones explícitas de retry

## Backend API

- `POST /api/backoffice/onboarding-processes`
- `GET /api/backoffice/onboarding-processes/{id}`
- `GET /api/backoffice/onboarding-processes`
- `POST /api/backoffice/onboarding-processes/{id}/retry`
- `GET /api/backoffice/onboarding-processes/{id}/result`

## Modelo de UX

- submit inicial síncrono
- seguimiento asíncrono
- errores de validación separados de errores de proceso
- read model orientado a UI
- sin push en v1
- sin front-end orchestration cross-service

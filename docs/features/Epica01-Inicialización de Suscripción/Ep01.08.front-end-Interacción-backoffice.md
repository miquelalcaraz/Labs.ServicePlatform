# **01.Interacción del front-end/backoffice**

# 1. Objetivo del diseño front-end

El backoffice debe permitir que un usuario interno de QLT System, principalmente un `ProjectManager`, pueda:

- iniciar el onboarding de un customer
- visualizar el progreso del proceso
- entender en qué punto está bloqueado
- reintentar pasos fallidos
- consultar el resultado final del alta

Y debe hacerlo sobre una arquitectura donde:

- el inicio del proceso es síncrono
- parte del flujo es asíncrono
- la consistencia es eventual
- los servicios se comunican por eventos

Eso obliga a diseñar la UX y los contratos API de forma explícita para **long-running workflows**

---

# 2. Principio clave de diseño

El front-end **no debe orquestar microservicios**.

El front-end debe hablar con una **surface de aplicación coherente**, y esa surface debe exponer:

- comandos síncronos
- consultas de estado
- acciones de retry
- vistas de progreso

La orquestación real debe seguir estando en backend, principalmente en `Account`, apoyado por `Identity` y `Notifications`.

---

# 3. Qué necesita realmente el Backoffice

Para esta épica, el backoffice necesita cuatro capacidades principales:

## A. Start onboarding

Formulario para iniciar el alta.

## B. Read onboarding status

Consulta detallada del proceso.

## C. Retry onboarding

Acción explícita para reintentar cuando falle.

## D. Read resulting entities

Consulta del `Subscription`, `Tenant`, `OwnerCompany`, `AdminUser`, `UserMembership`.

---

# 4. UX flow recomendado para onboarding

## Flujo general

### Pantalla 1 — Customer Onboarding List

Listado de onboardings / customers recientes.

Debe permitir:

- buscar
- filtrar por estado
- ver onboardings fallidos
- entrar al detalle

### Pantalla 2 — Start Onboarding

Formulario de creación.

Campos mínimos:

- `Company Legal Name`
- `Trade Name` opcional
- `Tax Id` opcional
- `Country Code` opcional
- `Subscription Plan Code`
- `Admin First Name`
- `Admin Last Name`
- `Admin Email`
- `Preferred Language` opcional

Acción:

- `Start Onboarding`

### Pantalla 3 — Onboarding Detail

Pantalla central del proceso.

Debe mostrar:

- resumen general
- estado global
- paso actual
- timeline de hitos
- errores si existen
- acciones disponibles

### Pantalla 4 — Customer Detail

Cuando el onboarding esté completado, acceso a la vista del customer ya creado:

- `Subscription`
- `Tenant`
- `OwnerCompany`
- `AdminUser`
- `Membership`

---

# 5. UX concreta de la pantalla de detalle

Esta pantalla es la más importante.

## Secciones recomendadas

### Header

- `OnboardingProcessId`
- `Status`
- `CurrentStep`
- `StartedAtUtc`
- `LastUpdatedAtUtc`
- `InitiatedBy`

### Customer Summary

- `Company Legal Name`
- `Subscription Plan Code`
- `Admin Email`

### Progress Tracker

Visualización step-based:

```
1. Subscription Created
2. Tenant Created
3. Owner Company Created
4. Admin Provisioning Requested
5. Admin User Provisioned
6. Admin Membership Created
7. Activation Requested
8. Activation Delivered
9. User Activated / Completed
```

Cada step debe verse como:

- `Completed`
- `Current`
- `Pending`
- `Failed`

### Technical / Operational Detail

- `CorrelationId`
- `LastErrorCode`
- `LastErrorMessage`
- `RetryCount`

Esto puede ir en una sección plegable si no quieres saturar la UI.

### Actions

Según estado:

- `Retry Onboarding`
- `Resend Activation`
- `Go to Customer`
- `Refresh`

# 6. Estrategia UX para estados asíncronos

## Regla principal

El usuario interno no debe pensar que el proceso ha terminado solo porque el submit respondió `200` o `202`.

Por tanto, tras crear el onboarding, la UX debe pasar automáticamente a una pantalla/estado de seguimiento.

## Comportamiento recomendado

Cuando el usuario pulsa `Start Onboarding`:

### El backend responde

- creación aceptada
- ids relevantes
- estado inicial del proceso

### La UI hace redirect a:

- `Onboarding Detail`

Y desde ahí:

- empieza polling
- muestra progreso real

---

# 7. Polling

## Frecuencia recomendada

### Fase activa

Cada `3–5 segundos` mientras:

- `Status = InProgress`
- `WaitingForExternalProvisioning`
- `WaitingForActivationDelivery`

### Fase de espera humana

Cuando el estado sea:

- `WaitingForUserActivation`

entonces reducir a:

- cada `20–30 segundos`
o incluso detener el polling activo y dejar refresh manual con aviso visual

## Cuándo parar el polling

- `Completed`
- `Failed`
- `Cancelled` si existiera

## Futuro: V2

SignalR puede tener sentido después, sobre todo para:

- backoffice operativo
- dashboards
- procesos largos
- notificaciones en tiempo real

# Resumen Ejecutivo — Implementación Épica 01-01: Refinamiento Inicialización de Suscripción

## 1. Objetivo

Refinar la implementación inicial de la Épica 01 (Inicialización de Suscripción) en dos iteraciones:

1. **Refinamiento 00 — Modelo de dominio detallado:** Enriquecer los 5 agregados de dominio con ciclos de vida completos (estados, transiciones, guards), factory methods especializados, y alinear la nomenclatura de commands y integration events con el lenguaje ubicuo del dominio.

2. **Refinamiento 01 — State Machine OnboardingProcess:** Reemplazar el modelo de avance genérico (`AdvanceTo`) por una máquina de estados dual (Status + Step) con 10 métodos explícitos de transición, cada uno con validación de precondiciones.

Ambos refinamientos se construyen sobre la base de la Épica 01-00 sin romper contratos existentes, siguiendo el principio de la plataforma: *"Platform evolves, services sleep peacefully"*.

## 3. Refinamiento 01 — State Machine OnboardingProcess

### Alcance

Rediseñar `OnboardingProcess` como una máquina de estados formal con modelo dual Status + Step, según el documento `01.State Machine-OnboardingProcess.md`.

### Modelo dual Status + Step

**OnboardingStatus** (macro-estado — en qué fase del proceso estamos):

```
Draft → InProgress → WaitingForExternalProvisioning → InProgress →
  WaitingForActivationDelivery → WaitingForUserActivation → Completed
                        ↓ (desde cualquier no-terminal)
                      Failed → (Retry) → InProgress
```

**OnboardingStep** (milestone — último hito alcanzado):

```
None → SubscriptionCreated → TenantCreated → OwnerCompanyCreated →
  AdminProvisioningRequested → AdminUserProvisioned → AdminMembershipCreated →
  ActivationRequested → ActivationDelivered → Completed
```

### Cambios en enums

| Enum | Cambios |
|------|---------|
| `OnboardingStatus` | Eliminado `PartiallyCompleted`. Añadidos `WaitingForExternalProvisioning(3)`, `WaitingForActivationDelivery(4)`, `WaitingForUserActivation(5)`. Renumerados `Completed(6)`, `Failed(7)` |
| `OnboardingStep` | Añadido `None(0)`. Renombrado `AdminUserProvisioningRequested` → `AdminProvisioningRequested`, `ActivationNotificationRequested` → `ActivationRequested`. Añadido `ActivationDelivered(8)`. Renumerado `Completed(9)` |

### API del agregado — Antes vs Después

| Antes (Épica 01-00) | Después (Refinamiento 01) |
|---------------------|--------------------------|
| `Create()` → InProgress / SubscriptionCreated | `Create()` → **Draft / None** |
| `AdvanceTo(OnboardingStep)` genérico | **10 métodos `Mark*()` específicos** |
| `SetOwnerCompany(companyId)` | Integrado en `MarkOwnerCompanyCreated(companyId)` |
| `SetAdminUser(userId)` | Integrado en `MarkAdminUserProvisioned(userId)` |
| `Complete()` sin validación | `Complete()` V1 con validación de datos |
| `Fail()` sin FailedStep | `Fail()` registra `FailedStep = CurrentStep` |
| Sin retry | `Retry()` con `RetryCount` + `LastRetryAtUtc` |

### Métodos de transición implementados

| Método | Precondición Status | Precondición Step | Efecto en Status | Efecto en Step |
|--------|:------------------:|:-----------------:|:----------------:|:--------------:|
| `Start()` | Draft | — | InProgress | (sin cambio) |
| `MarkSubscriptionCreated()` | InProgress | None | (sin cambio) | SubscriptionCreated |
| `MarkTenantCreated()` | InProgress | SubscriptionCreated | (sin cambio) | TenantCreated |
| `MarkOwnerCompanyCreated(companyId)` | InProgress | TenantCreated | (sin cambio) | OwnerCompanyCreated |
| `MarkAdminProvisioningRequested()` | InProgress | OwnerCompanyCreated | **WaitingForExternalProvisioning** | AdminProvisioningRequested |
| `MarkAdminUserProvisioned(userId)` | WaitingForExternalProvisioning | AdminProvisioningRequested | **InProgress** | AdminUserProvisioned |
| `MarkAdminMembershipCreated()` | InProgress | AdminUserProvisioned | (sin cambio) | AdminMembershipCreated |
| `MarkActivationRequested()` | InProgress | AdminMembershipCreated | **WaitingForActivationDelivery** | ActivationRequested |
| `MarkActivationDelivered()` | WaitingForActivationDelivery | ActivationRequested | **WaitingForUserActivation** | ActivationDelivered |
| `MarkUserActivated()` | WaitingForUserActivation | ActivationDelivered | **Completed** | Completed |

### Propiedades nuevas en OnboardingProcess

| Propiedad | Tipo | Propósito |
|-----------|------|-----------|
| `RetryCount` | `int` | Contador de reintentos acumulados |
| `LastRetryAtUtc` | `DateTimeOffset?` | Timestamp del último retry |

  → MarkSubscriptionCreated()
  → MarkTenantCreated()

## 7. Decisiones de arquitectura relevantes

### Modelo dual Status + Step

Se eligió un modelo de dos dimensiones en lugar de un único enum porque:
- **Status** comunica el estado general al exterior (UI, APIs, dashboards)
- **Step** rastrea el progreso granular para la lógica interna del handler
- Las precondiciones de cada transición validan **ambas dimensiones** (`EnsureStatus` + `EnsureStep`), eliminando transiciones inválidas por construcción

### Métodos Mark* explícitos vs AdvanceTo genérico

Se reemplazó `AdvanceTo(step)` por 10 métodos específicos porque:
- Cada transición tiene precondiciones únicas (status + step + parámetros)
- El compilador garantiza que cada handler llama al método correcto
- Los efectos secundarios (asignar CompanyId, cambiar Status) están encapsulados en cada método
- Eliminados los métodos standalone `SetOwnerCompany()` y `SetAdminUser()` del agregado

### Complete() V1 como atajo temporal

`Complete()` existe como conveniencia V1 mientras los pasos de activación (steps 7-9: ActivationRequested → ActivationDelivered → UserActivated) no están implementados. Valida datos mínimos (OwnerCompanyId + AdminUserId) y salta directamente a `Completed/Completed`.

### Retry preserva CurrentStep

Cuando se hace `Retry()`, el `CurrentStep` no se resetea. El handler de retry debe inspeccionar el step actual para determinar desde dónde continuar. Esto permite recovery granular sin repetir pasos ya completados.

## 8. Limitaciones conocidas y trabajo futuro

| Item | Detalle | Prioridad |
|------|---------|-----------|
| Pasos 7-9 del onboarding | ActivationRequested → ActivationDelivered → UserActivated no implementados (requiere Notifications service) | Media |
| Retry handler | No existe endpoint ni handler para reintentar un onboarding fallido. `Retry()` existe en el agregado pero no hay orquestación | Media |
| Query endpoints para OnboardingProcess | No existe `GET /api/accounts/onboarding/{id}` para consultar estado | Media |
| Complete() V1 | Atajo temporal que salta los pasos de activación. Debe eliminarse cuando se implemente el flujo completo | Baja |
| Retry desde WaitingForExternalProvisioning | Tras `Retry()` el status vuelve a `InProgress` pero el step queda en `AdminProvisioningRequested`, lo cual no coincide con las precondiciones de `MarkAdminUserProvisioned()` (requiere `WaitingForExternalProvisioning`). El handler de retry deberá re-invocar `MarkAdminProvisioningRequested()` o el patrón de recovery debe redefinirse | Baja |
| Migración EF pendiente | Los cambios en OnboardingProcess (5 propiedades nuevas) y enums actualizados requieren nueva migración | Alta |
| Migración Identity pendiente | `FirstName`, `LastName`, `UserType`, `UserStatus` en ApplicationUser sin migración | Alta (heredado de 01-00) |

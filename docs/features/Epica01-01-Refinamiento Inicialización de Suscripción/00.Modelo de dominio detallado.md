# 02. Modelo de dominio detallado

# Modelo de dominio detallado — Epic 1

## Scope de esta primera iteración

Nos centramos en el alta inicial de un cliente B2B, contemplando:

- creación de `Subscription`
- creación de `Tenant`
- creación de `OwnerCompany`
- provisión de `AdminUser`
- creación de `UserMembership`
- seguimiento del proceso mediante `OnboardingProcess`

Y teniendo en cuenta tres microservicios existentes:

- `Account`
- `Identity`
- `Notifications`

---

# 1. Bounded Context: Account

`Account` debe ser el **source of truth** de la estructura de negocio del cliente B2B.

## Responsabilidades

- gestionar `Tenant`
- gestionar `Company`
- gestionar `Subscription`
- gestionar la vinculación de usuarios al contexto de negocio mediante `UserMembership`
- gestionar el flujo de inicialización con `OnboardingProcess`

## No responsabilidades

- credenciales
- password
- MFA
- login/logout
- tokens
- autorización técnica de APIs
- envío de emails

---

# 2. Aggregate design en Account

## 2.1 Aggregate: Subscription

### Propósito

Representa el derecho de uso contratado por el cliente para acceder a la plataforma.

### Aggregate Root

`Subscription`

### Propiedades sugeridas

```
Subscription
- SubscriptionId
- TenantId
- OwnerCompanyId
- SubscriptionPlanCode
- Status
- StartDateUtc
- EndDateUtc
- CreatedAtUtc
- CreatedByInternalUserId
- ActivatedAtUtc
- SuspendedAtUtc
- CancelledAtUtc
```

### Invariantes

- una `Subscription` debe pertenecer a un único `Tenant`
- una `Subscription` debe estar asociada a una única `OwnerCompany`
- no puede pasar a `Active` sin `Tenant`
- no puede pasar a `Active` sin `OwnerCompany`
- no puede pasar a `Active` sin `AdminUser` provisionado y vinculado
- un `SubscriptionPlanCode` debe existir en el catálogo soportado por negocio

### Estados recomendados

```
SubscriptionStatus
- PendingInitialization
- Active
- Suspended
- Cancelled
```

### Comportamientos

- `Initialize(...)`
- `Activate(...)`
- `Suspend(...)`
- `Cancel(...)`
- `AttachTenant(...)`
- `AttachOwnerCompany(...)`

### Observación de modelado

Aunque conceptualmente `Subscription` nace al inicio del onboarding, yo la modelaría como aggregate propio y no embebida en `Tenant`, porque tiene ciclo de vida y reglas propias.

---

## 2.2 Aggregate: Tenant

### Propósito

Representa el límite organizativo y lógico donde vivirán una o varias empresas del cliente.

### Aggregate Root

`Tenant`

### Propiedades sugeridas

```
Tenant
- TenantId
- Name
- Status
- OwnerCompanyId
- CreatedAtUtc
- CreatedByInternalUserId
- ActivatedAtUtc
- ClosedAtUtc
```

### Invariantes

- un `Tenant` debe tener exactamente una `OwnerCompany`
- un `Tenant` puede tener múltiples `Companies`
- la `OwnerCompany` debe pertenecer al mismo `Tenant`
- no deben existir dos `OwnerCompany` dentro del mismo `Tenant`
- un `Tenant` no puede cerrarse si tiene una `Subscription` activa

### Estados recomendados

```
TenantStatus
- Pending
- Active
- Suspended
- Closed
```

### Comportamientos

- `Create(...)`
- `SetOwnerCompany(...)`
- `Activate(...)`
- `Suspend(...)`
- `Close(...)`

### Decisión importante

No metería aquí la colección completa de `Companies` si el aggregate se va a volver demasiado grande. En DDD práctico con Azure SQL, es razonable que `Tenant` mantenga la referencia a `OwnerCompanyId` y que `Company` sea aggregate propio.

---

## 2.3 Aggregate: Company

### Propósito

Representa una entidad empresarial dentro de un `Tenant`.

### Aggregate Root

`Company`

### Propiedades sugeridas

```
Company
- CompanyId
- TenantId
- LegalName
- TradeName
- TaxId
- CountryCode
- CompanyType
- Status
- CreatedAtUtc
- CreatedByInternalUserId
```

### Invariantes

- toda `Company` pertenece a un único `Tenant`
- la primera `Company` creada en el onboarding debe ser `Owner`
- una `Owner` company no puede existir sin `Tenant`
- una `Subscription` solo puede apuntar a una `Company` de tipo `Owner`
- el `TaxId`, si se usa, debe ser único al menos dentro del tenant o según la regla global que decidáis

### Estados recomendados

```
CompanyStatus
- Pending
- Active
- Inactive
```

### Tipos recomendados

```
CompanyType
- Owner
- Affiliate
- Branch
- Partner
```

Para la épica 1 solo usaríais `Owner`.

### Comportamientos

- `CreateOwnerCompany(...)`
- `CreateAffiliateCompany(...)`
- `Activate(...)`
- `Deactivate(...)`

### Nota

Aunque `Branch` y `Affiliate` no entren ahora, dejar el enum preparado evita renombrados futuros.

---

## 2.4 Aggregate: UserMembership

### Propósito

Representa la relación de un usuario con el contexto de negocio del sistema.

No representa identidad.

Representa **pertenencia y rol contextual**.

### Aggregate Root

`UserMembership`

### Propiedades sugeridas

```
UserMembership
- MembershipId
- UserId
- TenantId
- CompanyId
- MembershipType
- RoleCode
- Status
- IsPrimary
- CreatedAtUtc
- CreatedByInternalUserId
- ActivatedAtUtc
- RevokedAtUtc
```

### Invariantes

- un `UserMembership` debe apuntar a un `UserId` existente en `Identity`
- un `External` membership debe estar asociado a `TenantId` y `CompanyId`
- el primer usuario administrador del onboarding debe pertenecer a la `OwnerCompany`
- un usuario externo no puede tener membership en un tenant inexistente
- el rol asignado debe ser válido para el tipo de membership
- solo puede existir un `IsPrimary = true` por combinación que defináis, normalmente por usuario y tenant o por usuario y company

### Estados recomendados

```
MembershipStatus
- PendingActivation
- Active
- Inactive
- Revoked
```

### Tipos recomendados

```
MembershipType
- External
- Internal
```

### Roles contextuales recomendados

```
RoleCode
- TenantAdmin
- CompanyAdmin
- CompanyManager
- CompanyUser
```

### Comportamientos

- `CreateExternalAdminMembership(...)`
- `Activate(...)`
- `Revoke(...)`
- `ChangeRole(...)`

### Importante

**no usar `UserMembership` para internal users** salvo necesidad muy concreta.

Los `InternalUsers` deben resolverse principalmente en `Identity` con roles de plataforma.

Se puede dejar el enum `MembershipType`, pero en la práctica, para esta épica, `UserMembership` debería modelar **external access context**.

## 2.5 Aggregate: OnboardingProcess

### Propósito

Representa el proceso de inicialización del cliente y la trazabilidad de los pasos ejecutados.

Ayuda para la distribución con eventos.

### Aggregate Root

`OnboardingProcess`

### Propiedades sugeridas

```
OnboardingProcess
- OnboardingProcessId
- SubscriptionId
- TenantId
- OwnerCompanyId
- AdminUserId
- Status
- CurrentStep
- ErrorCode
- ErrorMessage
- StartedAtUtc
- CompletedAtUtc
- FailedAtUtc
- InitiatedByInternalUserId
- CorrelationId
```

### Invariantes

- debe existir como máximo un onboarding activo por `SubscriptionId`
- un onboarding completado no puede volver a `InProgress`
- un onboarding fallido puede pasar a reintento si el modelo lo soporta
- el proceso solo puede pasar a `Completed` si:
    - existe `Subscription`
    - existe `Tenant`
    - existe `OwnerCompany`
    - existe `AdminUser` en `Identity`
    - existe `UserMembership`
    - se ha solicitado la activación o invitación correspondiente

### Estados recomendados

```
OnboardingStatus
- Draft
- InProgress
- Completed
- Failed
- PartiallyCompleted
```

### Pasos recomendados

```
OnboardingStep
- SubscriptionCreated
- TenantCreated
- OwnerCompanyCreated
- AdminUserProvisioningRequested
- AdminUserProvisioned
- AdminMembershipCreated
- ActivationNotificationRequested
- Completed
```

### Comportamientos

- `Start(...)`
- `MarkStepCompleted(...)`
- `MarkFailed(...)`
- `MarkCompleted(...)`
- `Retry(...)`

### Decisión de diseño

Este aggregate no es solo técnico.

Tiene valor de negocio-operación porque permite:

- ver el estado del onboarding desde backoffice
- reintentar con seguridad
- auditar incidencias
- soportar eventual consistency

# 4. Identity domain model

`Identity` es el dueño de la identidad y del acceso técnico.

## 4.1 Aggregate / Entity: IdentityUser

### Propósito

Representa una identidad autenticable del sistema, interna o externa.

### Propiedades sugeridas

```
IdentityUser
- UserId
- Email
- FirstName
- LastName
- DisplayName
- UserType
- Status
- PreferredLanguage
```

### Invariantes

- el email debe ser único según la regla definida por Identity
- `UserType` debe ser `Internal` o `External`
- un usuario deshabilitado no debe autenticarse
- un usuario externo puede existir antes de tener membership activa
- un usuario interno nunca debe convertirse accidentalmente en admin de tenant sin pasar por reglas explícitas

### Tipos recomendados

```
UserType
- Internal
- External
```

### Estados recomendados

```
UserStatus
- PendingActivation
- Active
- Locked
- Disabled
```

### Comportamientos

- `ProvisionExternalUser(...)`
- `ProvisionInternalUser(...)`
- `Activate(...)`
- `Lock(...)`
- `Disable(...)`

---

## 4.2 Roles en Identity

Se separa en dos familias.

### Platform roles

Para usuarios internos:

```
PlatformRole
- SalesRepresentative
- ProjectManager
- BusinessAdmin
- SupportAgent
- PlatformAdmin
```

### Access model para externos

Para usuarios externos, no no utilizar toda la semántica de tenant/company como role global en Identity.

Mejor Resolver `Account` vía `UserMembership`.

Identity puede emitir claims base como:

- `sub`
- `email`
- `user_type`
- roles globales si son internos

Las APIs del dominio consultan memberships en `Account` cuando necesiten contexto de tenant/company.

# 5. Internal users vs external users

## Internal users

Usuarios de QLT System:

- sales representatives
- project managers
- business users
- support
- admins

### Ownership

- viven en `Identity`
- acceden a backoffice
- se autorizan con `PlatformRole`

### No deberían

- depender de `Tenant`
- depender de `Company`
- mezclarse con roles de cliente

---

## External users

Usuarios del cliente:

- admin inicial
- futuros usuarios del tenant

### Ownership

- identidad en `Identity`
- pertenencia de negocio en `Account` a través de `UserMembership`

# 11. Flujo de onboarding propuesto

## Paso 1

Un `ProjectManager` inicia `StartCustomerOnboardingCommand` desde Backoffice.

## Paso 2

`Account` crea:

- `Subscription`
- `Tenant`
- `OwnerCompany`
- `OnboardingProcess`

y publica:

- `CustomerAdminProvisioningRequestedIntegrationEvent`

## Paso 3

`Identity` consume ese evento y crea:

- `IdentityUser` con `UserType = External`
- `Status = PendingActivation`

y publica:

- `ExternalUserProvisionedIntegrationEvent`

## Paso 4

`Account` consume ese evento y crea:

- `UserMembership` con rol inicial, recomendado `TenantAdmin`

## Paso 5

`Account` actualiza `OnboardingProcess`

y, según el reparto que decidáis, publica algo tipo:

- `ActivationNotificationRequestedIntegrationEvent`

o espera a que `Identity` lo haga.

## Paso 6

`Notifications` envía el email de activación.

## Paso 7

Cuando el proceso mínimo está completo, `Account` marca:

- `OnboardingProcess = Completed`
- `Subscription = Active` si esa es vuestra regla

# 12. Reglas de negocio explícitas

## Subscription rules

- A `Subscription` must belong to exactly one `Tenant`.
- A `Subscription` must reference exactly one `OwnerCompany`.
- A `Subscription` cannot become `Active` until onboarding is completed.

## Tenant rules

- A `Tenant` must have exactly one `OwnerCompany`.
- A `Tenant` may contain multiple `Companies`.
- A `Tenant` cannot be closed while an active `Subscription` exists.

## Company rules

- The first `Company` in a new `Tenant` must be of type `Owner`.
- Only an `Owner` company can own a `Subscription`.

## User rules

- Every external admin must first exist in `Identity`.
- An external user must have at least one `UserMembership` to operate in the platform context.
- Internal users must be managed through `PlatformRoles`.

## Onboarding rules

- Only authorized internal users can start onboarding.
- Onboarding must be idempotent.
- Duplicate provisioning messages must not create duplicate users.
- Duplicate membership creation attempts must be safely ignored or merged.

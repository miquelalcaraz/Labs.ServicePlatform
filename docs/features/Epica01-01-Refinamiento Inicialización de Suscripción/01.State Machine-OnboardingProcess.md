# State Machine — `OnboardingProcess`

## 1. Objetivo del `OnboardingProcess`

El `OnboardingProcess` representa el ciclo de alta inicial de un customer B2B desde que un `ProjectManager` lanza el proceso hasta que:

- el `Tenant` existe
- la `OwnerCompany` existe
- el `AdminUser` ha sido provisionado
- la `UserMembership` ha sido creada
- la activación ha sido solicitada
- el onboarding queda marcado como completado

Su misión no es solo orquestar, sino también:

- dar trazabilidad
- permitir reintentos seguros
- consolidar errores de negocio
- exponer estado comprensible en backoffice

---

# 2. Modelo de estado recomendado

Separar en dos conceptos:

## A. `Status`

Describe el estado general del proceso.

## B. `CurrentStep`

Describe el último hito confirmado del flujo.

Eso evita forzar toda la semántica en un único enum.

---

# 3. `OnboardingStatus`

## Enum recomendado

```
OnboardingStatus
- Draft
- InProgress
- WaitingForExternalProvisioning
- WaitingForActivationDelivery
- WaitingForUserActivation
- Completed
- Failed
- Cancelled
```

## Significado de cada estado

### `Draft`

El proceso existe pero todavía no se ha iniciado formalmente.

### `InProgress`

El proceso está ejecutando pasos internos del `Account Service`.

### `WaitingForExternalProvisioning`

`Account` ya ha hecho su parte inicial y está esperando respuesta de `Identity`.

### `WaitingForActivationDelivery`

`Identity` ya provisionó el usuario y el sistema está esperando que la comunicación de activación sea enviada o aceptada por `Notifications`.

### `WaitingForUserActivation`

La invitación/activación ya fue emitida, pero el usuario aún no ha activado su cuenta.

### `Completed`

El onboarding ha finalizado correctamente.

### `Failed`

El proceso ha fallado y requiere intervención o retry.

### `Cancelled`

El proceso fue abortado explícitamente.

Para v1 incluso podrías no implementarlo si todavía no necesitáis cancelaciones operativas.

---

# 4. `OnboardingStep`

## Enum recomendado

```
OnboardingStep
- None
- SubscriptionCreated
- TenantCreated
- OwnerCompanyCreated
- AdminProvisioningRequested
- AdminUserProvisioned
- AdminMembershipCreated
- ActivationRequested
- ActivationDelivered
- UserActivated
- Completed
```

## Regla conceptual

- `Status` dice “en qué macroestado está el proceso”
- `CurrentStep` dice “hasta qué hito hemos llegado”

Ejemplo:

- `Status = WaitingForUserActivation`
- `CurrentStep = ActivationDelivered`

Eso es mucho más expresivo que usar solo un enum.

---

# 5. Flujo nominal recomendado

Este sería el happy path.

## Step 0

Proceso creado.

```
Status = Draft
CurrentStep = None
```

## Step 1

El `ProjectManager` lanza onboarding y `Account` crea:

- `Subscription`
- `Tenant`
- `OwnerCompany`

```
Status = InProgress
CurrentStep = OwnerCompanyCreated
```

## Step 2

`Account` publica `CustomerAdminProvisioningRequestedIntegrationEvent`

```
Status = WaitingForExternalProvisioning
CurrentStep = AdminProvisioningRequested
```

## Step 3

`Identity` responde con `ExternalUserProvisionedIntegrationEvent`

```
Status = InProgress
CurrentStep = AdminUserProvisioned
```

## Step 4

`Account` crea `UserMembership`

```
Status = InProgress
CurrentStep = AdminMembershipCreated
```

## Step 5

`Identity` publica `UserActivationRequestedIntegrationEvent`

```
Status = WaitingForActivationDelivery
CurrentStep = ActivationRequested
```

## Step 6

`Notifications` publica `ActivationEmailSentIntegrationEvent`

```
Status = WaitingForUserActivation
CurrentStep = ActivationDelivered
```

## Step 7

`Identity` publica `UserActivatedIntegrationEvent`

```
Status = Completed
CurrentStep = Completed
```

# 6. Tabla de transiciones válidas

## Desde `Draft`

### Permitido

- `Start()` → `InProgress / SubscriptionCreated` o avance secuencial interno

### No permitido

- pasar directamente a `Completed`
- pasar a `WaitingForUserActivation`
- pasar a `Cancelled` sin haber iniciado, salvo que negocio lo pida

---

## Desde `InProgress`

### Permitido

- avanzar secuencialmente por pasos internos:
    - `SubscriptionCreated`
    - `TenantCreated`
    - `OwnerCompanyCreated`

### Permitido

- cuando se emite provisioning:
    - `WaitingForExternalProvisioning / AdminProvisioningRequested`

### Permitido

- `Failed`

### No permitido

- retroceder pasos
- marcar `Completed` sin pasar por provisioning/activation

---

## Desde `WaitingForExternalProvisioning`

### Permitido

- al llegar `ExternalUserProvisionedIntegrationEvent`:
    - `InProgress / AdminUserProvisioned`

### Permitido

- al llegar `UserProvisioningFailedIntegrationEvent`:
    - `Failed`

### Permitido

- retry controlado de provisioning

### No permitido

- avanzar a `WaitingForUserActivation` sin usuario provisionado
- completar onboarding

---

## Desde `WaitingForActivationDelivery`

### Permitido

- `ActivationEmailSentIntegrationEvent`:
    - `WaitingForUserActivation / ActivationDelivered`

### Permitido

- `ActivationEmailFailedIntegrationEvent`:
    - `Failed` o permanencia con retry, según política

### No permitido

- `Completed`
- `UserActivated` sin activación emitida, salvo que admitáis activación manual/alternativa

---

## Desde `WaitingForUserActivation`

### Permitido

- `UserActivatedIntegrationEvent`:
    - `Completed / Completed`

### Permitido

- reenvío de activación, manteniéndose en el mismo estado

### Permitido

- `Failed`, si queréis timeout o invalidación

### No permitido

- volver a `InProgress`
- borrar membership como parte normal del flujo

---

## Desde `Completed`

### Permitido

- ninguno, salvo operaciones de consulta

### No permitido

- cualquier transición de negocio normal
- retry
- fail posterior sobre el mismo onboarding

`Completed` debe ser terminal.

---

## Desde `Failed`

### Permitido

- `Retry()` → estado depende del punto de reintento
- `Cancelled()` si queréis cierre manual

### No permitido

- `Completed` directo sin rehacer el paso pendiente
- retroceder arbitrariamente sin política explícita

---

# 7. Notas sobre retries

## Observación

No hacer un `retry from scratch` ciego.

Haced **retry from failed step**.

Eso significa que el `OnboardingProcess` debe conservar:

- `CurrentStep`
- `FailedStep`
- `LastErrorCode`
- `RetryCount`

# 9. Reglas de transición recomendadas

## Regla 1

`CurrentStep` solo puede avanzar hacia delante.

## Regla 2

`Status = Completed` solo si se cumplen estas condiciones:

- `SubscriptionId` existe
- `TenantId` existe
- `OwnerCompanyId` existe
- `AdminUserId` existe
- membership creada
- activación de usuario completada

## Regla 3

Los eventos externos duplicados no deben provocar re-transiciones inválidas.

Ejemplo:

- si llega dos veces `ExternalUserProvisionedIntegrationEvent`
- y ya estamos en `AdminMembershipCreated`
- ignorar o registrar como duplicado inocuo

## Regla 4

No se puede crear más de un onboarding activo por `SubscriptionId`.

## Regla 5

Los fallos externos deben dejar el proceso en estado observable y accionable.

# 10. Eventos que disparan transiciones

## Comandos internos de `Account`

- `CancelCustomerOnboardingCommand` opcional

## Eventos externos

- `ExternalUserProvisionedIntegrationEvent`
- `UserProvisioningFailedIntegrationEvent`
- `UserActivationRequestedIntegrationEvent`
- `ActivationEmailSentIntegrationEvent`
- `ActivationEmailFailedIntegrationEvent`
- `UserActivatedIntegrationEvent`

# 11. Transition map propuesto

## A. Inicio

```
Draft
  -> StartCustomerOnboardingCommand
  -> InProgress / SubscriptionCreated
```

## B. Construcción de estructura base

```
InProgress / SubscriptionCreated
  -> TenantCreated
  -> InProgress / TenantCreated

InProgress / TenantCreated
  -> OwnerCompanyCreated
  -> InProgress / OwnerCompanyCreated
```

## C. Solicitud de provisioning

```
InProgress / OwnerCompanyCreated
  -> CustomerAdminProvisioningRequestedIntegrationEvent published
  -> WaitingForExternalProvisioning / AdminProvisioningRequested
```

## D. Respuesta de Identity

```
WaitingForExternalProvisioning / AdminProvisioningRequested
  -> ExternalUserProvisionedIntegrationEvent
  -> InProgress / AdminUserProvisioned

WaitingForExternalProvisioning / AdminProvisioningRequested
  -> UserProvisioningFailedIntegrationEvent
  -> Failed / AdminProvisioningRequested
```

## E. Membership

```
InProgress / AdminUserProvisioned
  -> Create UserMembership
  -> InProgress / AdminMembershipCreated
```

## F. Activación

```
InProgress / AdminMembershipCreated
  -> UserActivationRequestedIntegrationEvent
  -> WaitingForActivationDelivery / ActivationRequested
```

```
WaitingForActivationDelivery / ActivationRequested
  -> ActivationEmailSentIntegrationEvent
  -> WaitingForUserActivation / ActivationDelivered
```

```
WaitingForActivationDelivery / ActivationRequested
  -> ActivationEmailFailedIntegrationEvent
  -> Failed / ActivationRequested
```

## G. Activación completada

```
WaitingForUserActivation / ActivationDelivered
  -> UserActivatedIntegrationEvent
  -> Completed / Completed
```

# 12. Qué hacer con `UserActivationRequestedIntegrationEvent`

Aquí hay dos opciones de modelado.

## Opción recomendada

Tratarlo como hito observable del proceso.

Cuando `Account` lo conoce:

```
Status = WaitingForActivationDelivery
CurrentStep = ActivationRequested
```

Esto es útil porque separa:

- el momento en que la activación es solicitada
- del momento en que el email realmente fue enviado

Y eso mejora bastante soporte y troubleshooting.

---

# 13. Estados terminales

## `Completed`

Terminal, inmutable salvo auditoría.

## `Cancelled`

Terminal, opcional.

## `Failed`

No necesariamente terminal si soportáis retry.

Yo lo modelaría como **quasi-terminal**:

- no avanza por sí mismo
- solo puede salir por `Retry()`

---

# 14. Política de retry recomendada

## Fallo en provisioning de usuario

Caso:

- email duplicado
- conflicto de identidad
- validación funcional

### Política

- dejar `Failed`
- permitir retry manual desde backoffice
- idealmente tras corregir datos

## Fallo en envío de activation email

Caso:

- template no disponible
- proveedor caído
- rechazo temporal

### Política

- se puede permitir retry automático limitado
- luego retry manual

## Timeout de activación por usuario

Caso:

- el usuario no activa en X días

### Política recomendada v1

- mantener `WaitingForUserActivation`
- no marcar `Failed` automáticamente al inicio
- resolver después con procesos operativos aparte

---

# 15. Modelo de transiciones inválidas

Conviene dejarlo explícito para desarrollo.

## Ejemplos inválidos

- `Draft -> Completed`
- `WaitingForExternalProvisioning -> Completed`
- `InProgress / TenantCreated -> WaitingForUserActivation`
- `Completed -> Failed`
- `Completed -> Retry`
- `Failed -> Completed` sin rehacer el paso necesario

---

# 16. Reglas de implementación

## A. El aggregate debe validar transiciones

No lo dejéis solo al handler o a la UI.

## B. Los handlers deben ser idempotentes

Si un mismo evento llega dos veces:

- no duplicar side effects
- no romper la state machine

## C. Los side effects se disparan fuera del aggregate

El aggregate decide estado.

La publicación al bus y la persistencia van en application/infrastructure.

# 17. Propuesta de API del aggregate

Conceptualmente, el aggregate podría exponer algo así:

```
Start(...)
MarkSubscriptionCreated(...)
MarkTenantCreated(...)
MarkOwnerCompanyCreated(...)
MarkAdminProvisioningRequested(...)
MarkAdminUserProvisioned(...)
MarkAdminMembershipCreated(...)
MarkActivationRequested(...)
MarkActivationDelivered(...)
MarkUserActivated(...)
MarkFailed(...)
Retry(...)
Cancel(...)
```

## Recomendación

Aunque esto parezca verboso, creo que es mejor que un método genérico tipo:

- `AdvanceTo(step)`

Porque:

- expresa intención
- encapsula invariantes
- evita transiciones absurdas

---

# 18. Reglas concretas por método

## `Start(...)`

Solo desde `Draft`.

## `MarkSubscriptionCreated(...)`

Solo desde `InProgress` y `CurrentStep = None` o inmediatamente después de `Start`.

## `MarkTenantCreated(...)`

Solo si ya existe `SubscriptionCreated`.

## `MarkOwnerCompanyCreated(...)`

Solo si ya existe `TenantCreated`.

## `MarkAdminProvisioningRequested(...)`

Solo si ya existe `OwnerCompanyCreated`.

## `MarkAdminUserProvisioned(...)`

Solo desde `WaitingForExternalProvisioning`.

## `MarkAdminMembershipCreated(...)`

Solo si `AdminUserProvisioned` ya ocurrió.

## `MarkActivationRequested(...)`

Solo si `AdminMembershipCreated` ya ocurrió.

## `MarkActivationDelivered(...)`

Solo desde `WaitingForActivationDelivery`.

## `MarkUserActivated(...)`

Solo desde `WaitingForUserActivation`.

## `MarkCompleted(...)`

Solo si `UserActivated` ya ocurrió.

## `MarkFailed(...)`

Permitido desde cualquier estado no terminal.

## `Retry(...)`

Solo desde `Failed`.

# 20. Mi recomendación final de simplificación para v1

Para no sobrediseñar, state machine mínima:

## Status

```
Draft
InProgress
WaitingForExternalProvisioning
WaitingForActivationDelivery
WaitingForUserActivation
Completed
Failed
```

## Step

```
None
SubscriptionCreated
TenantCreated
OwnerCompanyCreated
AdminProvisioningRequested
AdminUserProvisioned
AdminMembershipCreated
ActivationRequested
ActivationDelivered
Completed
```

Y de momento no añadir:

- `Cancelled`
- timeouts automáticos
- subestados complejos
- compensaciones automáticas

---

# 21. Qué gana el sistema con este enfoque

Con esta state machine tenemos:

- trazabilidad completa de onboarding
- soporte más fácil desde backoffice
- retry seguro
- mejor observabilidad cross-service
- una base muy limpia para event handlers

# 04.Mapa ejecutivo de interacción Frontend/API

# Mapa ejecutivo de interacción Frontend/API para Epic 2

## 1. Principio rector

Mantendría exactamente el mismo principio de Epic 1:

> el front no orquesta servicios; consume una API de backoffice coherente, con comandos síncronos y consultas de estado/read models
> 

Eso ya fue una decisión explícita en Epic 1 y sigue siendo la más adecuada para un proceso largo, asíncrono y event-driven.

---

## 2. Qué cambia funcionalmente en Epic 2

Epic 1 terminaba cuando existían:

- `Subscription`
- `Tenant`
- `OwnerCompany`
- `AdminUser`
- `AdminMembership`

y el onboarding se daba por completo ahí.

Epic 2 añade una segunda fase:

- solicitar activación
- enviar email
- esperar activación real del usuario
- marcar customer como activo / ready / live

Eso implica una nueva surface de backoffice para gestionar **Activation Processes**.

# 3. Propuesta de UX de Epic 2

Yo lo estructuraría en **3 pantallas principales + 1 acción integrada**.

---

## Pantalla A — Activation List

### Ruta sugerida

```
/activation
```

### Objetivo

Listado de procesos de activación de clientes.

### Reutiliza de Epic 1

Es casi un espejo de `Onboarding List`:

- grid server-side
- filtros
- badges de estado
- acciones contextuales
- navegación a detalle

### Columnas recomendadas

- `Company Legal Name`
- `Admin Email`
- `Subscription Plan`
- `Activation Status`
- `Current Step`
- `Started At`
- `Last Updated`
- `Retries`
- `Actions`

### Filtros recomendados

- `status`
- `companyLegalName`
- `adminEmail`
- `subscriptionPlanCode`

### Acciones

- `View`
- `Retry`
- `Resend Activation`
- opcional: `Open Customer`

---

## Pantalla B — Activation Detail

### Ruta sugerida

```
/activation/{id}
```

### Objetivo

Pantalla principal operativa de Epic 2.

### Reutiliza de Epic 1

La estructura puede ser casi idéntica a `Onboarding Detail`, que ya estaba pensada como pantalla rica de long-running workflow: header, summary cards, step tracker, error panel, acciones y technical details.

### Secciones recomendadas

### Header

- `ActivationProcessId`
- `Status`
- `CurrentStep`
- `StartedAtUtc`
- `LastUpdatedAtUtc`

### Summary

- `Company Legal Name`
- `Subscription Plan Code`
- `Admin Email`

### Progress tracker

Steps propuestos para Epic 2:

```
1. Activation Requested
2. Activation Delivered
3. User Activated
4. Customer Ready
5. Completed
```

Cada step:

- `Completed`
- `Current`
- `Pending`
- `Failed`

### Error section

- `LastErrorCode`
- `LastErrorMessage`
- `OccurredAtUtc`

### Technical detail

- `CorrelationId`
- `SubscriptionId`
- `TenantId`
- `OwnerCompanyId`
- `AdminUserId`
- `AdminMembershipId`
- `RetryCount`

### Action bar

- `Back to List`
- `Refresh`
- `Retry`
- `Resend Activation`
- `Open Customer`

---

## Pantalla C — Activation Result

### Ruta sugerida

```
/activation/{id}/result
```

### Objetivo

Mostrar el resultado final de la activación, equivalente conceptual al `/result` de onboarding.

### Cuándo aporta valor

Aunque no siempre es imprescindible, encaja muy bien con el patrón que ya montasteis en Epic 1:

- detalle operativo durante el proceso
- result view cuando ya está completado.

### Qué mostraría

- `Subscription`
- `Tenant`
- `OwnerCompany`
- `AdminUser`
- `AdminMembership`
- `Activation status`
- `ActivatedAtUtc`
- `GoLiveAtUtc` si lo introducís

---

## Acción integrada en Customer Detail

Además de esas tres pantallas, añadiría una acción desde la futura vista de customer o desde el result de onboarding:

### Acción

```
Start Activation
```

### Comportamiento

- si no existe proceso de activación → lo crea
- si ya existe → redirige a detalle
- evita duplicidad

Esto os permite encadenar Epic 1 → Epic 2 de forma muy natural desde UX.

# 4. Flujo UX recomendado

## Happy path

```
Onboarding Result
→ Start Activation
→ redirect a Activation Detail
→ polling
→ Activation Delivered
→ Waiting for User Activation
→ User activates account
→ Completed
→ Open Customer
```

## Failure path

```
Activation Detail
→ status Failed
→ show last error
→ Retry or Resend Activation
```

## Espera humana

El estado más especial es:

```
WaitingForUserActivation
```

Aquí repetiría la decisión acertada de Epic 1:

- bajar la frecuencia de polling
- permitir refresh manual
- mostrar mensaje claro de espera humana

Ese patrón ya estaba previsto en el diseño original aunque luego el cierre real de Epic 1 simplificara el flujo.

# 5. Propuesta de API de Backoffice para Epic 2

Mantendría exactamente la misma filosofía que en Epic 1:

- endpoints orientados a caso de uso
- no exponer aggregates puros
- read models específicos de UI
- `202 Accepted` en acciones asíncronas
- error contract homogéneo.

---

## 5.1 Start activation

### Endpoint

```
POST /api/backoffice/activation-processes
```

### Purpose

Crear/iniciar un `CustomerActivationProcess`.

### Request sugerida

```
{
  "subscriptionId":"guid",
  "tenantId":"guid",
  "ownerCompanyId":"guid",
  "adminUserId":"guid",
  "adminMembershipId":"guid"
}
```

### Response

```
202 Accepted
```

```
{
  "activationProcessId":"guid",
  "status":"WaitingForNotificationDelivery",
  "currentStep":"ActivationRequested",
  "statusDisplayName":"Waiting for Activation Delivery",
  "currentStepDisplayName":"Activation Requested",
  "startedAtUtc":"2026-04-09T10:15:00Z",
  "links": {
    "self":"/api/backoffice/activation-processes/guid",
    "result":"/api/backoffice/activation-processes/guid/result"
  }
}
```

### Recomendación

Soportar `x-requestid`, igual que onboarding.

## 5.4 Retry activation process

### Endpoint

```
POST /api/backoffice/activation-processes/{activationProcessId}/retry
```

### Request

```
{
  "reason":"Retry requested after notification delivery failure."
}
```

### Response

```

```

```
{
  "activationProcessId":"guid",
  "status":"WaitingForNotificationDelivery",
  "currentStep":"ActivationRequested",
  "retryCount":1,
  "links": {

  }
}
```

## 5.5 Resend activation

### Endpoint

```
POST /api/backoffice/activation-processes/{activationProcessId}/resend-activation
```

### Purpose

Volver a solicitar el envío del email sin crear un nuevo proceso.

### Request

Opcionalmente vacío o con `reason`.

### Response

```
202 Accepted
```

# 8. Polling strategy para Epic 2

Aquí sí haría un pequeño ajuste respecto a Epic 1.

## Estados de polling activo

Cada `5–10s`:

- `InProgress`
- `WaitingForNotificationDelivery`

## Estados de espera humana

Cada `25–30s` o manual:

- `WaitingForUserActivation`

## Estados terminales

Stop polling:

- `Completed`
- `Failed`

Esto sigue exactamente la lógica conceptual ya diseñada en la state machine de Epic 1 para activación, y también la recomendación de no tratar la espera del usuario como un proceso intensivo de sistema.

# 11. Mi recomendación cerrada

Si lo resumimos en una línea:

> Epic 2 front-end/API debería replicar el patrón de backoffice de Epic 1, pero sobre un nuevo proceso `CustomerActivationProcess`, con pantallas de List/Detail/Result, polling adaptativo y endpoints orientados a UI para `start`, `detail`, `list`, `retry`, `resend` y `result`.
> 

Y, siendo pragmático, yo haría esta primera versión mínima:

- `GET /api/backoffice/activation-processes`
- `GET /api/backoffice/activation-processes/{id}`
- `POST /api/backoffice/activation-processes/{id}/retry`
- `POST /api/backoffice/activation-processes/{id}/resend-activation`
- `GET /api/backoffice/activation-processes/{id}/result`

Y dejaría `POST /api/backoffice/activation-processes` solo si el proceso necesita arranque manual desde UI; si arranca automáticamente al terminar Epic 1, no hace falta exponerlo en la primera iteración.

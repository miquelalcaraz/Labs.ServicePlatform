# 05.Front-End / Backoffice / API Specification

## **Customer Activation & Go-Live**

---

## **1. Purpose**

Epic 1 dejó resuelto el **customer provisioning** inicial desde backoffice: creación de `Subscription`, `Tenant`, `OwnerCompany`, `AdminUser` y `AdminMembership`, con seguimiento operativo desde el backoffice mediante listados, detalle, retry, result y read models orientados a UI. La implementación final de Epic 1 cerró el onboarding en el momento en que la membership del admin ya existía, dejando fuera el activation flow real del usuario.

Epic 2 debe cerrar ese hueco y cubrir la siguiente fase del lifecycle:

- solicitar activación del admin user
- enviar la comunicación de activación
- esperar la activación real del usuario
- marcar al customer como listo / live

El objetivo no es reabrir el `OnboardingProcess` de Epic 1, sino construir una segunda fase explícita, coherente con la decisión ya tomada al cierre de la épica anterior.

---

## **2. Scope**

Esta especificación cubre la interacción necesaria entre:

- **Backoffice Front-End**
- **Backoffice API**
- **Account Service**
- **Identity Service**
- **Notifications Service**

y define:

- la surface de API necesaria para backoffice
- las pantallas mínimas
- el flujo de navegación y estados
- la estrategia de polling
- la autorización por rol
- los read models orientados a UI

No define en detalle la implementación interna de Identity o Notifications, aunque sí condiciona qué información deben emitir o consumir por eventos.

---

## **3. Architectural Principles**

### **3.1 Thin client**

Se mantiene el principio adoptado en Epic 1:

> The front-end must not orchestrate microservices.
> 

El front-end debe consumir una **application surface coherente**, con:

- comandos síncronos
- lecturas orientadas a UI
- acciones explícitas de retry
- acciones explícitas de resend
- estado de proceso preparado para mostrarse directamente

### **3.2 Account owns process state**

`Account` sigue siendo el owner del proceso de negocio y del estado del proceso de activación, del mismo modo que en Epic 1 fue owner del onboarding. `Identity` sigue siendo owner de autenticación/activación real del usuario, y `Notifications` del envío de comunicaciones.

### **3.3 Backoffice API as UI-oriented surface**

Igual que en Epic 1, los endpoints de backoffice no deben exponer aggregates puros, sino **DTOs / read models orientados a pantalla**, con display names, actions y estructura lista para rendering.

### **3.4 Event-driven backend, simple frontend**

El backend seguirá siendo event-driven y eventual consistent. El front-end no debe inferir estados compuestos ni llamar directamente a `Identity` o `Notifications`.

## **4. Conceptual Model**

Epic 2 introduce un nuevo proceso de negocio:

## **`CustomerActivationProcess`**

Su responsabilidad es cubrir la fase comprendida entre:

- el customer ya provisionado
- y el customer realmente activado / listo para operar

### **Recommended lifecycle**

La recomendación es modelarlo como un proceso separado del onboarding, no como extensión del `OnboardingProcess`, porque Epic 1 ya quedó formalmente cerrado cuando se estableció la membership del admin.

### **Suggested statuses**

```
ActivationStatus
- Draft
- InProgress
- WaitingForNotificationDelivery
- WaitingForUserActivation
- Completed
- Failed
```

### **Suggested steps**

```
ActivationStep
- None
- ActivationRequested
- ActivationDelivered
- UserActivated
- CustomerReady
- Completed
```

Este modelo mantiene el patrón dual `Status + Step` ya usado con éxito en `OnboardingProcess`.

---

## **5. Functional Goal of Epic 2**

Epic 2 debe transformar un customer desde:

```
Provisioned
```

hasta:

```
Activated / Ready / Live
```

### **Business meaning**

Un customer se considera realmente operativo cuando:

- el admin user ha recibido activación
- el admin user ha activado su cuenta
- el sistema considera al tenant/customer listo para operar

En la primera iteración, `CustomerReady` puede resolverse automáticamente tras `UserActivated`, sin exigir configuración adicional obligatoria. Esa simplificación deja abierta una futura evolución hacia readiness manual o guided setup.

## **7. UX Flow**

### **7.1 Happy path**

```
Onboarding Result
→ Start Activation
→ Activation Detail
→ Waiting for Notification Delivery
→ Waiting for User Activation
→ User activates account
→ Completed
→ Open Customer
```

### **7.2 Failure path**

```
Activation Detail
→ Failed
→ show error
→ Retry or Resend Activation
```

### **7.3 Human waiting state**

El estado más especial de la UX es:

```
WaitingForUserActivation
```

Debe tratarse como espera humana, no como actividad intensiva del sistema. Por tanto:

- polling más espaciado
- posibilidad de refresh manual
- mensaje claro y operativo

## **8. API Surface**

La surface API recomendada para Epic 2 replica la filosofía de Epic 1:

- endpoints de caso de uso
- respuestas orientadas a UI
- `202 Accepted` para acciones asíncronas
- error contract homogéneo
- idempotencia basada en request id

**Endpoint**

```
POST /api/backoffice/activation-processes
```

**Purpose** Crear o iniciar un `CustomerActivationProcess`.

**Request**

```json
  "subscriptionId": "guid",
  "tenantId": "guid",
  "ownerCompanyId": "guid",
  "adminUserId": "guid",
  "adminMembershipId": "guid"
}
```

**Success**

```
202 Accepted
```

```json
{
  "activationProcessId": "guid",
  "status": "WaitingForNotificationDelivery",
  "currentStep": "ActivationRequested",
  "statusDisplayName": "Waiting for Activation Delivery",
  "currentStepDisplayName": "Activation Requested",

    "self": "/api/backoffice/activation-processes/guid",

}
```

**Notes**

- Debe soportar `x-requestid`
- Puede no ser necesario exponerlo en UI si el proceso arranca automáticamente

## **9. Error Contract**

Epic 2 debe reutilizar el error contract homogéneo consolidado al cierre de Epic 1.

**Canonical shape**

```json
{
  "code": "ValidationError",
  "message": "One or more validation errors occurred.",
  "traceId": "string",
  "details": null,
  "errors": {
    "field": ["message"]
  }
}
```

Esto aplica a:

- validación
- not found
- conflict
- retry not allowed
- resend not allowed
- invalid state

## **12. Polling Strategy**

Epic 2 debe reutilizar el patrón de polling adaptativo de Epic 1, ajustándolo al nuevo ciclo.

### **Active polling**

Cada `5–10 segundos` en:

- `InProgress`
- `WaitingForNotificationDelivery`

### **Human waiting polling**

Cada `25–30 segundos` o manual en:

- `WaitingForUserActivation`

### **Stop polling**

- `Completed`
- `Failed`

## **14. Front-End State Model**

La SPA debe mantener dos niveles de estado:

### **A. Command state**

Para acciones inmediatas:

- submitting
- success
- error

### **B. Process state**

Para el workflow largo:

- `status`
- `currentStep`
- `steps`
- `lastError`
- `actions`
- `references`

No se deben mezclar ambos niveles en un único estado ambiguo.

## **17. MVP Recommendation**

Si hay que priorizar una primera versión mínima de Epic 2, la recomendación es:

### **Required**

- `GET /api/backoffice/activation-processes`
- `GET /api/backoffice/activation-processes/{id}`
- `POST /api/backoffice/activation-processes/{id}/retry`
- `POST /api/backoffice/activation-processes/{id}/resend-activation`
- `GET /api/backoffice/activation-processes/{id}/result`

### **Optional**

- `POST /api/backoffice/activation-processes`

Solo será necesario exponer `POST /activation-processes` si el proceso necesita arranque manual. Si el backend puede iniciarlo automáticamente al terminar Epic 1, este endpoint puede quedar interno o posponerse.

---

## **18. Final Recommendation**

La recomendación cerrada para Epic 2 es:

> Repetir el patrón exitoso de Epic 1 para el backoffice, pero aplicándolo a un nuevo proceso `CustomerActivationProcess`, con una única surface API orientada a UI, tres pantallas principales (`List`, `Detail`, `Result`), polling adaptativo, autorización por rol y acciones explícitas de `retry` y `resend activation`.
> 

Esto os permite:

- mantener consistencia de producto
- reutilizar patrones ya consolidados
- no reabrir semánticamente Epic 1
- cerrar por fin el ciclo completo de alta de suscripción

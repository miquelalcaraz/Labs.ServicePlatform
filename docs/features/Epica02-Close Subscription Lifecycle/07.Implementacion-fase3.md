## Objetivo

Conectar el ciclo de vida de onboarding (Epic 1) con el ciclo de activación (Epic 2) de forma idempotente y resiliente. Cuando `ExternalUserProvisionedIntegrationEventHandler` completa el onboarding, dispara automáticamente `StartCustomerActivationProcessCommand`, preservando la correlación y garantizando el handoff incluso ante replays del evento.

## Entregables

### 1. Handoff automático en `ExternalUserProvisionedIntegrationEventHandler`

#### 1.1 Inyección de `IMediator`

`IMediator` añadido como nueva dependencia para poder dispatchar el comando a través del pipeline completo (idempotency behavior + transaction behavior + logging behavior).

#### 1.2 Guard `Completed` mejorado — Replay resilience

**Antes:**
```csharp
if (onboarding.Status == OnboardingStatus.Completed)
{
    _logger.LogInformation("... already completed. Ignoring duplicate event.");
    return;
}
```

**Después:**
```csharp
if (onboarding.Status == OnboardingStatus.Completed)
{
    _logger.LogInformation("... already completed. Ensuring activation handoff.");
    await SendStartActivationCommandAsync(@event, onboarding);
    return;
}
```

El retorno prematuro silencioso era un gap: si el onboarding se completaba pero el activation command fallaba, un replay posterior del evento no reintentaría el handoff. Ahora el comando se despacha también en el path de replay.

#### 1.3 Dispatch de activación en el path normal

Tras `SaveChangesAsync()` exitoso, se dispara el comando de activación pasando `membership.Id` (el ID de la membresía recién creada):

```csharp
await _membershipRepository.UnitOfWork.SaveChangesAsync();

_logger.LogInformation("Account - UserMembership created and onboarding completed...");

await SendStartActivationCommandAsync(@event, onboarding, membership.Id);
```

#### 1.4 Método `SendStartActivationCommandAsync`

Método privado que construye y despacha `StartCustomerActivationProcessCommand`:

```
@event.OnboardingProcessId  → RequestId  (idempotency key determinístico)
@event.SubscriptionId       → SubscriptionId
@event.TenantId             → TenantId
@event.CompanyId            → OwnerCompanyId
@event.UserId               → AdminUserId
@event.Email                → AdminEmail
membership.Id               → AdminMembershipId  (path normal)
onboarding.AdminMembershipId → AdminMembershipId  (path de replay)
onboarding.CompanyLegalName  → CompanyLegalName   (snapshot opcional)
onboarding.SubscriptionPlanCode → SubscriptionPlanCode (snapshot opcional)
```

El resultado se evalúa sin lanzar excepción: `IsFailure` → log warning; `IsSuccess` → log info. Fallos de activación no revierten el onboarding ya completado.

## Capas de idempotencia

El handoff es idempotente en tres niveles:

| Capa | Mecanismo | Dónde |
|------|-----------|-------|
| 1 | `RequestId = @event.OnboardingProcessId` — misma clave en `IdempotencyEntry` para cualquier replay del mismo evento | `IdempotencyBehavior` (pipeline) |
| 2 | Guard `GetBySubscriptionIdAsync` — si ya existe un proceso activo para la suscripción, retorna `Result.Success(true)` | `StartCustomerActivationProcessCommandHandler` |
| 3 | Guard `Completed` mejorado — en replay, omite mutaciones del onboarding pero aun así despacha el comando | `ExternalUserProvisionedIntegrationEventHandler` |

## Decisiones de Diseño

1. **`@event.OnboardingProcessId` como `RequestId`:** La clave de idempotencia del comando se deriva del ID del proceso de onboarding, que es estable y único por suscripción. Esto garantiza que replays del mismo `ExternalUserProvisionedIntegrationEvent` no creen procesos de activación duplicados, incluso si el `IdempotencyEntry` ya expiró (el guard de `SubscriptionId` en el handler actúa como segunda línea).

2. **`IMediator.Send` en lugar de acceso directo al repositorio:** Dispatchar el comando a través del pipeline activa `IdempotencyBehavior`, `TransactionBehavior` y `LoggingBehavior`, reutilizando toda la lógica de la capa de aplicación sin duplicarla en el handler de integración.

3. **Fallos de activación como warnings, no como excepciones:** Si `StartCustomerActivationProcessCommand` retorna `Result.Failure`, se registra como warning pero no se lanza excepción. El onboarding ya está completado y persistido — revertirlo o reencolar el mensaje sería incorrecto. El backoffice puede reiniciar la activación vía `RetryCustomerActivationProcess` si es necesario.

4. **Guard `Completed` mejorado sin romper el contrato de idempotencia del onboarding:** El guard sigue impidiendo duplicar las mutaciones del onboarding (membership + domain transitions). Solo añade la llamada al comando de activación, que internamente es idempotente por diseño.

5. **Factory `CreateHandler` con mock condicional:** El mock de `IMediator` solo se configura con el setup por defecto cuando no se pasa uno externo. Esto permite a los tests que necesitan capturar la llamada (via `Callback`) pasar su propio mock sin que el factory lo sobreescriba.

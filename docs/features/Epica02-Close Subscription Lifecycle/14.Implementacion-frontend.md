# Epic 2 — Frontend Implementation

## Overview

Implement the backoffice frontend for `CustomerActivationProcess`, replicating the Epic 1 pattern (`Onboarding*`) applied to the new process. The API surface is complete and covered by functional tests. The frontend consists of three pages (`List`, `Detail`, `Result`) plus their supporting service and models.

**Entry points confirmed from functional tests:**
- `GET  /api/backoffice/activation-processes`
- `GET  /api/backoffice/activation-processes/{id}`
- `POST /api/backoffice/activation-processes/{id}/retry`
- `POST /api/backoffice/activation-processes/{id}/resend`  ← confirmed path (not `/resend-activation`)
- `GET  /api/backoffice/activation-processes/{id}/result`  ← backend endpoint pending

- `ActivationProcessResultResponse`: adds `ActivationResultResponse` nested record with `ActivatedAtUtc` and `GoLiveAtUtc`

### `Services/ActivationApiService.cs` ✅

Typed HTTP client implemented as planned. Actual signatures:

```csharp
public class ActivationApiService(HttpClient httpClient, ILogger<ActivationApiService> logger)
{
    private const string BasePath = "/api/backoffice/activation-processes";

    Task<ApiResult<ActivationProcessDetailResponse>>   GetActivationDetailAsync(Guid id, ...)
    Task<ApiResult<ActivationProcessListResponse>>     GetActivationListAsync(string? status, string? companyLegalName, string? adminEmail, string? subscriptionPlanCode, int page, int pageSize, string sortBy, string sortDirection, ...)
    Task<ApiResult<ActivationProcessRetryResponse>>    RetryActivationAsync(Guid id, RetryActivationRequest? request, ...)
    Task<ApiResult<ActivationProcessResendResponse>>   ResendActivationAsync(Guid id, ResendActivationRequest? request, ...)
    Task<ApiResult<ActivationProcessResultResponse>>   GetActivationResultAsync(Guid id, ...)
}
```

**Notes:**
- `Retry` and `Resend` both add `x-requestid` header with a new `Guid.NewGuid()`
- `Resend` sends empty body `{}` — confirmed by functional tests
- All methods return `ApiResult<T>` (reuse existing class from `OnboardingApiService.cs`)

**Key difference vs Epic 1: two-speed adaptive polling**

```csharp
private static bool ShouldPoll(string status)
    => status is "InProgress" or "WaitingForNotificationDelivery" or "WaitingForUserActivation";

private static int GetPollingInterval(string status) => status switch
{
    "WaitingForUserActivation"       => 30,   // human wait — relaxed
    "WaitingForNotificationDelivery" => 10,
    _                                => 5     // InProgress — active
};
```

Action handlers:
- `RetryAsync()` — calls `Api.RetryActivationAsync`, reloads, restarts polling
- `ResendAsync()` — calls `Api.ResendActivationAsync`, shows notification (no state change expected)

Badge helpers:
```csharp
private static BadgeStyle GetStatusBadgeStyle(string status) => status switch
{
    "Completed"                      => BadgeStyle.Success,
    "Failed"                         => BadgeStyle.Danger,
    "InProgress"                     => BadgeStyle.Info,
    "WaitingForNotificationDelivery" => BadgeStyle.Warning,
    "WaitingForUserActivation"       => BadgeStyle.Warning,
    _                                => BadgeStyle.Secondary

private static BadgeStyle GetStepBadgeStyle(string stepStatus) => stepStatus switch
{
    "Completed" => BadgeStyle.Success,

    "Failed"    => BadgeStyle.Danger,

```

Context messages for human-wait state (shown below progress tracker):
```
WaitingForNotificationDelivery → "Activation has been requested. Waiting for notification delivery."
WaitingForUserActivation       → "Activation email delivered. Waiting for the customer admin to activate the account."
Failed                         → "Activation process failed. Review the error details and retry or resend activation."
```

### `Detail.razor`

Sections (mirror `Onboarding/Detail.razor` layout):
1. **Header** — `ActivationProcessId`, `Status` badge, `CurrentStep`, `StartedAtUtc`, `LastUpdatedAtUtc`
2. **Summary cards** — `CompanyLegalName`, `SubscriptionPlanCode`, `AdminEmail`
3. **Progress tracker** — 5 steps: `ActivationRequested` → `ActivationDelivered` → `UserActivated` → `CustomerReady` → `Completed`; each step shows badge per `step.Status`
4. **Context message** — conditional message panel for `WaitingForUserActivation` and `Failed` states
5. **Error section** — conditional, shown when `detail.LastError != null`: `Code`, `Message`, `OccurredAtUtc`
6. **Technical details** — collapsible: `CorrelationId`, `SubscriptionId`, `TenantId`, `OwnerCompanyId`, `AdminUserId`, `AdminMembershipId`, `RetryCount`
7. **Action bar** — `Back to List`, `Refresh`, `Retry` (when `detail.Actions.CanRetry`), `Resend Activation` (when `detail.Actions.CanResendActivation`), `Open Result` (when `Completed`)

## E2E Enablement ✅

To validate the complete activation flow end-to-end, the following backend components were implemented alongside the frontend:

### Identity — `ConfirmEmail` Razor Page

`src/Qlt.Infrastructure/Qlt.Infrastructure.Identity/Pages/Account/ConfirmEmail/Index.cshtml[.cs]`

- `OnGetAsync(string? userId)`: finds user by ID, calls `user.Activate()` + sets `EmailConfirmed = true`, publishes `UserActivatedIntegrationEvent` via outbox
- `ConfirmEmailStatus` enum: `Error`, `Success`, `AlreadyConfirmed`
- Decorated with `[SecurityHeaders]` + `[AllowAnonymous]`
- 7 unit tests covering all branches (`ConfirmEmailModelTests.cs`)

### EmailService — Activation Link

`IEmailService.SendActivationEmailAsync` updated with `Guid adminUserId` parameter. `EmailService` includes the activation link in the email body:

```
https://identity/Account/ConfirmEmail?userId={adminUserId}
```

### E2E Functional Test

`BackOfficeActivationApiTests.ActivationProcess_WhenUserActivatesAccount_ProcessCompletes`

Simulates the full flow without the message bus:
1. `StartActivationAndGetId` — seeds process with controlled `adminUserId`
2. Calls `ActivationDeliveredIntegrationEventHandler` directly → advances to `WaitingForUserActivation`
3. Calls `UserActivatedIntegrationEventHandler` directly → `Complete()`
4. Asserts `GET /{id}` returns `Status == "Completed"`

> Handlers are constructed directly from DI-resolved dependencies to bypass the EF idempotency decorator chain (context-tracking conflict on retry in the test environment).

## Key Differences from Epic 1

| Aspect | Epic 1 (Onboarding) | Epic 2 (Activation) |
|--------|---------------------|---------------------|
| Mutation actions | `Retry` only | `Retry` + `Resend` |
| Polling speeds | 5s (InProgress), 10s (WaitingForExternal) | 5s (InProgress), 10s (WaitingForNotificationDelivery), **30s (WaitingForUserActivation)** |
| Steps | 4 | **5** (ActivationRequested → ActivationDelivered → UserActivated → CustomerReady → Completed) |
| Step model | `Code`, `DisplayName`, `Status` | `Code`, `DisplayName`, `Status`, **`CompletedAtUtc`** |
| List actions | `CanOpen`, `CanRetry` | `CanOpen`, `CanRetry`, **`CanResendActivation`** |
| Detail actions | `CanRetry`, `CanRefresh`, `CanOpenCustomer` | `CanRetry`, **`CanResendActivation`**, `CanRefresh`, `CanOpenCustomer` |
| Result shape | Subscription + Tenant + OwnerCompany + AdminUser + AdminMembership | Same + **`ActivationResultResponse`** (ActivatedAtUtc, GoLiveAtUtc) |
| Resend endpoint | — | `POST /{id}/resend` (empty body `{}`) |

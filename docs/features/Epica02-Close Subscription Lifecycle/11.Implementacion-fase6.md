## Patrón de setup: creación de procesos vía MediatR

Los tests de API necesitan procesos de activación existentes pero no hay un endpoint POST de creación (los procesos se crean automáticamente por el handoff desde onboarding). El helper `StartActivationAndGetId` resuelve esto usando `IMediator` directamente a través del `IServiceScope` del `WebApplicationFactory`:

```csharp
private async Task<Guid> StartActivationAndGetId(string? adminEmail = null, string? companyLegalName = null)
{
    using var scope = _webApplicationFactory.Services.CreateScope();
    var mediator = scope.ServiceProvider.GetRequiredService<IMediator>();

    await mediator.Send(new StartCustomerActivationProcessCommand(
        subscriptionId: Guid.NewGuid(),
        tenantId: Guid.NewGuid(),
        ownerCompanyId: Guid.NewGuid(),
        adminUserId: Guid.NewGuid(),
        adminMembershipId: Guid.NewGuid(),
        companyLegalName: companyLegalName,
        subscriptionPlanCode: "PROFESSIONAL",
        adminEmail: adminEmail,
        requestId: Guid.NewGuid()),
        TestContext.Current.CancellationToken);

    var listResult = await mediator.Send(
        new GetCustomerActivationProcessListQuery(
            Status: null, CompanyLegalName: null, AdminEmail: adminEmail,
            Page: 1, PageSize: 10),
        TestContext.Current.CancellationToken);

    return listResult.Value.Items[0].ActivationProcessId;
}
```

Ventajas frente a otras alternativas:
- No requiere endpoint de creación ni seed SQL directo.
- Pasa por el pipeline completo (transaction behavior, idempotency behavior, domain events).
- Los datos quedan en el mismo estado que produciría el sistema en producción.

### Positivos (autorización pasa, lógica de negocio responde)

La estrategia para los tests positivos es usar un `Guid.NewGuid()` como ID de proceso: si el rol pasa la autorización, el endpoint llega al handler y devuelve `404 NotFound` (proceso no existe). Si el rol fuera denegado, devolvería `403`. El `404` actúa como evidencia de que la autorización fue superada.

## Deuda técnica — Flujo E2E cross-service

Los tests de flujo completo (onboarding → activation → email → delivery → user activated → go-live) no se implementan en esta fase. Requieren:

- Arranque del stack completo de Aspire (Service Bus / RabbitMQ, Notifications, Identity).
- Espera de procesamiento asíncrono del outbox y del event bus entre servicios.
- Estrategia de polling o webhooks para observar el estado final del proceso.

Estos tests se consideran candidatos para una suite de tests de aceptación / smoke tests de release, no para la suite de integración habitual.

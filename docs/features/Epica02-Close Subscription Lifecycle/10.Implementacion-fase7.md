## Objetivo

Endurecer la infraestructura de los servicios implicados en el ciclo de activación antes de escribir los tests end-to-end (Fase 6), garantizando que las sondas de salud, las métricas de dominio y la trazabilidad de logs estén en su lugar y funcionen en todos los entornos.

---

## Hallazgos de Exploración

El análisis previo a la implementación identificó cuatro gaps que, de no corregirse, producirían fallos silenciosos en producción o harían imposible diagnosticar incidencias en el ciclo de activación:

| # | Gap identificado | Impacto |
|---|-----------------|---------|
| 1 | Health endpoints solo expuestos en `Development` | K8s liveness/readiness probes fallarían en staging/production |
| 2 | `AddQltSDBContext` no registra health check de SQL Server | `/health/ready` sería `Healthy` aunque la base de datos fuera inalcanzable |
| 3 | Sin métricas de dominio para el ciclo de activación | Sin visibilidad del volumen de procesos iniciados, completados y fallidos |
| 4 | `CorrelationId` ausente del scope de logs en el handler de Notifications | Logs no correlacionables entre servicios en dashboards estructurados |

## Entregables

### A. Health Endpoints en todos los entornos

**Archivo:** `src/Qlt.Platform/Qlt.Platform.ServiceDefaults/Builders/Extensions.cs`

`MapDefaultEndpoints` exponía `/health` y `/alive` solo dentro del guard `app.Environment.IsDevelopment()`. Se eliminó el guard y se añadió el endpoint de readiness:

| Endpoint | Tag filter | Propósito |
|----------|-----------|-----------|
| `/health` | Todos los checks | Dashboard general |
| `/alive` | `live` | Liveness probe K8s |
| `/health/ready` | `ready` | Readiness probe K8s |

### B. SQL Server Health Check — Accounts

**Archivo:** `src/Qlt.Services/Qlt.Services.Accounts/Infrastructure/Extensions/Extensions.cs`

```csharp
services.AddHealthChecks()
    .AddDbContextCheck<AccountContext>(name: "accounts-db", tags: ["ready"]);
```

Registrado inmediatamente después de `AddQltReadDbContext`. Disponible en `/health/ready` con el tag `ready`.

> ⚠️ **Refactor pendiente (plataforma):** Cuando se implemente la mejora propuesta en [`docs/backlog/platform-observability-improvements.md`](../../../backlog/platform-observability-improvements.md#1-automatic-db-health-check-in-addqltsdcontext), este registro manual desaparecerá — quedará cubierto automáticamente por `AddQltSDBContext<TContext>`.

### C. SQL Server Health Check — Notifications

**Archivo:** `src/Qlt.Services/Qlt.Services.Notifications/Extensions/Extensions.cs`
**Paquete añadido:** `Microsoft.Extensions.Diagnostics.HealthChecks.EntityFrameworkCore v10.0.5`

```csharp
services.AddHealthChecks()
    .AddDbContextCheck<NotificationsContext>(name: "notifications-db", tags: ["ready"]);
```

Notifications usa `Microsoft.EntityFrameworkCore.SqlServer` directamente (no Aspire), por lo que el paquete de health checks debía añadirse explícitamente.

> ⚠️ **Refactor pendiente (plataforma):** Ídem al punto B. Cuando la mejora de plataforma esté disponible, la referencia al paquete y el registro manual se eliminarán.

### D. `CustomerActivationDiagnostics` — Métricas de dominio

**Archivo nuevo:** `src/Qlt.Services/Qlt.Services.Accounts/Application/CustomerActivationDiagnostics.cs`

Tres contadores registrados sobre `ApplicationDiagnostics.Meter` (fuente `"Qlt.Domain.Application"`, ya presente en el pipeline de OpenTelemetry — sin configuración adicional):

| Contador | Nombre OTel | Tag |
|----------|------------|-----|
| `ProcessesStarted` | `accounts.activation.processes.started` | `subscription_plan` |
| `ProcessesCompleted` | `accounts.activation.processes.completed` | — |
| `ProcessesFailed` | `accounts.activation.processes.failed` | `error_code` |

**Puntos de emisión:**

| Archivo | Evento | Contador |
|---------|--------|----------|
| `StartCustomerActivationProcessCommandHandler` | Proceso creado y persistido | `ProcessesStarted` |
| `UserActivatedIntegrationEventHandler` | `process.Complete()` + SaveChanges OK | `ProcessesCompleted` |
| `UserActivatedIntegrationEventHandler` | `catch AccountDomainException` | `ProcessesFailed (error_code: UserActivatedProcessingError)` |
| `ActivationDeliveredIntegrationEventHandler` | `catch AccountDomainException` | `ProcessesFailed (error_code: ActivationDeliveredProcessingError)` |

### E. CorrelationId Log Scope — Notifications Handler

**Archivo:** `src/Qlt.Services/Qlt.Services.Notifications/IntegrationEvents/EventHandling/ActivationEmailRequestedIntegrationEventHandler.cs`

Todo el cuerpo del `Handle` envuelto en un scope estructurado:

```csharp
using (_logger.BeginScope(new Dictionary<string, object?>
{
    ["CorrelationId"] = @event.CorrelationId,
    ["ActivationProcessId"] = @event.ActivationProcessId
}))
```

Cada log emitido por el handler llevará automáticamente estos campos en Application Insights / Seq.

> ⚠️ **Refactor pendiente (plataforma):** Cuando se implemente `CorrelationIdLoggingIntegrationEventDecorator<T>` (ver [`docs/backlog/platform-observability-improvements.md`](../../../backlog/platform-observability-improvements.md#2-correlationidloggingintegrationeventdecoratort-in-platformmessaging)), la entrada `CorrelationId` del scope podrá eliminarse — el decorator la inyectará automáticamente en todos los handlers. El campo `ActivationProcessId` seguirá siendo responsabilidad del handler (requiere datos del repositorio, no del evento).

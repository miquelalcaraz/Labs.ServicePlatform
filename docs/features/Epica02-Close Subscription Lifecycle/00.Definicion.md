# 00.Definición

## 🎯 Objetivo estratégico

Completar el ciclo iniciado en Epic 1, pasando de:

> “estructura técnica provisionada”
> 
> 
> → a
> 
> “cliente operativo, activo y autónomo en la plataforma”
> 

En Epic 1 ya llegáis a:

- Tenant creado
- Subscription activa
- Owner Company creada
- Admin User provisionado + membership
- Onboarding marcado como **Completed (V1)**

👉 Pero **esto no implica que el cliente esté realmente activo** desde el punto de vista de negocio.

---

# 🧠 Concepto clave de Epic 2

Epic 2 introduce el concepto de:

## 👉 **Customer Activation Lifecycle**

Un ciclo separado del provisioning técnico que cubre:

1. Activación real del usuario
2. Primera entrada al sistema
3. Configuración mínima del tenant
4. Validación de readiness
5. Paso a estado **Go-Live**

---

# 🧩 Bloques funcionales (mapa conceptual)

## 1. 🔐 Activation Flow (Identity-driven)

### Problema actual

En Epic 1 eliminasteis el activation flow del dominio por falta de integración

### Qué entra en Epic 2

Reintroducir el flujo real:

- `ActivationEmailRequested`
- `ActivationDelivered`
- `UserActivated`

### Resultado

- El usuario pasa de:
    - `PendingActivation` → `Active`
- Se genera el evento:
    - `UserActivatedIntegrationEvent`

👉 Esto es el **trigger real de negocio**, no el provisioning.

---

## 2. 🔄 Reapertura del Onboarding (Phase 2)

### Decisión importante

No reutilizar el onboarding actual tal cual, sino:

👉 Opción recomendada:

- Extender el modelo como:
    - `OnboardingProcess V2`
    - o nuevo proceso: `CustomerActivationProcess`

### Nuevo objetivo del proceso:

```
AdminUserProvisioned →
ActivationRequested →
ActivationDelivered →
UserActivated →
CustomerReady →
GoLive
```

👉 Epic 1 termina en *provisioning*

👉 Epic 2 empieza en *activation*

---

## 3. 🏗️ Tenant Readiness / Minimum Configuration

Una vez el usuario activa:

### Validaciones necesarias

- Tenant activo
- Subscription activa
- Owner Company válida
- Admin Membership activa
- (opcional) configuración inicial:
    - idioma
    - branding
    - parámetros básicos

👉 Esto introduce un nuevo concepto:

## 👉 `TenantReadinessStatus`

Ejemplo:

- `NotReady`
- `PartiallyConfigured`
- `Ready`

---

## 4. 👤 First Login Experience (Backoffice + Customer UI)

### Flujo clave

1. Usuario recibe invitación
2. Activa cuenta
3. Hace login
4. Primera experiencia guiada

### Aquí entra:

- First login detection
- Optional onboarding wizard (customer-side)

👉 Este punto conecta backend + frontend.

---

## 5. 🚦 Go-Live State

Nuevo estado de negocio:

## 👉 `CustomerStatus`

Ejemplo:

- `Provisioned` (Epic 1)
- `Activated`
- `Ready`
- `Live`

### Transición clave:

```
UserActivated + TenantReady → CustomerLive
```

---

## 6. 🔔 Notifications Integration (ahora sí)

Epic 2 activa el rol real de Notifications:

- envío de activation email
- recordatorios
- notificaciones de fallo

Eventos clave:

- `ActivationEmailRequestedIntegrationEvent`
- `ActivationDeliveredIntegrationEvent`

---

## 7. 🧯 Failure & Recovery (Activation phase)

Nuevos casos:

- email no entregado
- usuario no activa
- token expirado

### Necesitas:

- retry activation
- resend invitation
- reissue activation token

---

## 8. 📊 Observabilidad de negocio

Ya tenéis observabilidad técnica muy sólida

Epic 2 añade:

- funnel de activación:
    - Provisioned → Activated → Live
- métricas:
    - activation rate
    - time to activation
    - drop-off

---

# ⚖️ Decisión clave de diseño (muy importante)

## ❗ Pregunta estratégica

¿Queréis que “onboarding” incluya activación o separarlo?

### Recomendación (más limpia en DDD)

👉 Separar en dos procesos:

1. **CustomerProvisioningProcess** (Epic 1)
2. **CustomerActivationProcess** (Epic 2)

Ventajas:

- bounded contexts claros
- menos complejidad en state machine
- mejor trazabilidad

---

# 🧭 Resumen ejecutivo (one-liner)

> Epic 2 transforma un cliente “provisionado” en un cliente “activo y operativo”, introduciendo el flujo real de activación de usuario, readiness del tenant y transición a Go-Live.
> 

---

# 🚀 Qué conseguirías al cerrar Epic 2

- Cliente puede entrar y usar la plataforma
- Flujo end-to-end completo (venta → uso real)
- Métricas de activación
- Base para billing, usage, features reales

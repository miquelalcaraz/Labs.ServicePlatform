## Handlers Implementados

### `ActivationDeliveredIntegrationEventHandler`

Consume `ActivationDeliveredIntegrationEvent` de `Qlt.Services.Notifications.Contracts`.

**Flujo del `Handle`:**

```
1. GetAsync(event.ActivationProcessId)
   ├─ null → LogWarning + return
   └─ Completed → LogInformation + return (idempotencia)
2. process.MarkActivationDelivered()
   → Status: WaitingForUserActivation
   → CurrentStep: ActivationDelivered
3. _repository.Update(process)
4. UnitOfWork.SaveChangesAsync()
5. [catch AccountDomainException]
   → process.Fail("ActivationDeliveredProcessingError", ex.Message)
   → Update + SaveChanges
```

### `UserActivatedIntegrationEventHandler`

Consume `UserActivatedIntegrationEvent` de `Qlt.Infrastructure.Identity.Contracts`.

**Flujo del `Handle`:**

```
1. GetByAdminUserIdAsync(event.UserId)
   ├─ null → LogWarning + return
   └─ Completed → LogInformation + return (idempotencia)
2. process.MarkUserActivated(event.UserId)
   → Status: InProgress
   → CurrentStep: UserActivated
   → Raises CustomerAdminActivatedDomainEvent
3. process.MarkCustomerReady()
   → CurrentStep: CustomerReady
4. process.Complete()
   → Status: Completed
   → CurrentStep: Completed
   → Raises CustomerGoLiveDomainEvent
5. _repository.Update(process)
6. UnitOfWork.SaveChangesAsync()
7. [catch AccountDomainException]
   → process.Fail("UserActivatedProcessingError", ex.Message)
   → Update + SaveChanges
```

## Decisiones de Diseño

1. **`GetByAdminUserIdAsync` en `UserActivatedIntegrationEventHandler`:** La búsqueda del proceso por `AdminUserId` en lugar de por un ID del proceso es la única opción viable: `UserActivatedIntegrationEvent` de Identity no incluye `ActivationProcessId`. El `AdminUserId` actúa como clave de correlación entre el mundo de Identity y el mundo de Accounts.

2. **`MarkUserActivated → MarkCustomerReady → Complete` en secuencia atómica:** Los tres pasos se ejecutan dentro del mismo handler y se guardan en una única llamada a `SaveChangesAsync`. No hay estados intermedios persistidos entre ellos, lo que simplifica la lógica de reintento: si cualquiera de los tres falla, el proceso entra en `Failed` y puede ser reintentado desde `WaitingForUserActivation`.

3. **Guard `Completed` con `LogInformation` (no warning):** El estado `Completed` ante un replay no es un problema — es el comportamiento esperado. Se registra como `Information` para distinguirlo semánticamente de casos genuinamente problemáticos.

4. **`AccountDomainException → Fail` en ambos handlers:** El catch de `AccountDomainException` permite que el proceso persista en estado `Failed` con el código de error, habilitando observabilidad y posibilidad de reintento manual desde el backoffice, en lugar de dejar el mensaje de integración en el dead-letter queue sin traza en el dominio.

5. **Tests con estado de dominio real (sin mocks del agregado):** Los tests avanzan el `CustomerActivationProcess` real a través de los métodos de dominio (`Start → RequestActivation → ...`) en lugar de usar mocks del agregado. Esto verifica la integración handler–dominio y detecta regresiones en las transiciones de estado.

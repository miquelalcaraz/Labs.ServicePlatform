|---------|-------------|

| `RetryCustomerActivationProcessCommand` | `IdempotentCommand<bool>`. Reintenta un proceso en estado `Failed`. Llama `Retry()` y, si el step es `ActivationRequested`, también `RestartActivationDelivery()`. |
| `ResendActivationEmailCommand` | `ICommand<bool>`. Reenvía el email de activación desde un proceso activo. Llama `RequestActivation()` nuevamente. |

### 4. Integration Event Handlers (incoming)

| Handler | Evento | Flujo |
|---------|--------|-------|
| `ActivationDeliveredIntegrationEventHandler` | `ActivationDeliveredIntegrationEvent` | Localiza proceso por `ActivationProcessId`. Guard de `Completed`. Llama `MarkActivationDelivered()`. Catch `AccountDomainException` → `Fail(code, message)`. |
| `UserActivatedIntegrationEventHandler` | `UserActivatedIntegrationEvent` | Localiza proceso por `AdminUserId` vía `GetByAdminUserIdAsync`. Guard de `Completed`. Llama `MarkUserActivated → MarkCustomerReady → Complete()` en secuencia atómica. Catch `AccountDomainException` → `Fail(code, message)`. |

**Patrón de resiliencia en handlers:**
- Guard `if (process.Status == Completed) return` antes de cualquier mutación.
- `AccountDomainException` se captura y redirige a `Fail()` para preservar el proceso en estado recuperable, evitando pérdida del mensaje de event bus.

## Decisiones de Diseño

1. **V1: `MarkCustomerReady()` automático tras `MarkUserActivated()`:** En `UserActivatedIntegrationEventHandler` se ejecutan `MarkUserActivated → MarkCustomerReady → Complete()` en secuencia dentro de la misma transacción. No se requiere readiness check adicional en MVP. Esto simplifica el flujo al eliminar un paso manual de backoffice y reduce la ventana de inconsistencia.

2. **`RestartActivationDelivery()` como método separado de `RequestActivation()`:** La distinción es semántica: `RequestActivation()` inicia la solicitud de email (solo desde `InProgress`), mientras que `RestartActivationDelivery()` reinicia el envío (solo desde `InProgress` con step `ActivationRequested`). Esto permite que `RetryCustomerActivationProcessCommand` decida automáticamente si solo necesita resetear el status o también reenviar el email, sin lógica de negocio fuera del agregado.

3. **Nuevo proyecto `Qlt.Services.Notifications.Contracts`:** Se crea como proyecto independiente siguiendo el patrón de `Accounts.Contracts` e `Identity.Contracts`. El path de referencias relativas usa `..\..\Qlt.Platform\...` (2 niveles desde `src\Qlt.Services\`) para respetar la estructura de directorios del repositorio. Esto garantiza que el servicio Notifications pueda publicar en su propio namespace sin acoplar sus contratos a Accounts.

4. **Handlers de integration events con `completed` guard + `Fail()` en dominio:** En lugar de lanzar excepciones que reencolarían el mensaje indefinidamente, los handlers capturan `AccountDomainException` y llaman a `Fail()`. El proceso queda en estado `Failed` recuperable vía backoffice (`RetryCustomerActivationProcess`). Esto evita poison messages y permite diagnóstico y corrección manual.

5. **Tests de capa de aplicación diferidos a Fase 7:** Los handlers de comandos, domain events e integration events se prueban mejor con tests de integración (in-memory DB + in-memory event bus) que con mocks. Se implementarán en la fase de hardening junto con los tests funcionales end-to-end.

6. **`BackOfficeActivationApi` como método estático:** Sigue el patrón establecido en Epic 1. El método `MapBackOfficeActivationApiV1(WebApplication app)` crea su propio grupo versionado internamente, siendo llamado desde `Program.cs` como `BackOfficeActivationApi.MapBackOfficeActivationApiV1(app)`.

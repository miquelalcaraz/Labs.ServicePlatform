# 04. Implementation Plan

## Epic 2: Close Subscription Lifecycle

Implement Epic 2 as a separate activation lifecycle (without reopening onboarding), delivered in two increments:

1. MVP for operational end-to-end flow.
2. Hardening for resilience and observability.

The implementation reuses proven patterns from Epic 1 across Accounts, Identity, and Notifications:

- Idempotent commands.
- Integration event handlers.
- Transactional outbox.
- Retry semantics.
- Backoffice API conventions.

## Scope

### Included

- End-to-end implementation across Accounts, Identity, Notifications, and backoffice activation API surface.
- New aggregate `CustomerActivationProcess` separated from `OnboardingProcess`.
- V1 simplification: automatic `CustomerReady` right after `UserActivated`.

### Excluded from MVP

- Customer-facing first-login wizard UX.
- Advanced policy engine for TenantReadiness beyond deterministic V1 checks.
- Downstream Billing/Usage consumers beyond emitting `CustomerGoLiveIntegrationEvent`.

## Phased Plan

### Phase 0: Baseline and Contract Alignment

1. Validate naming and event contract boundaries across services:
   - `ActivationEmailRequestedIntegrationEvent`
   - `ActivationDeliveredIntegrationEvent`
   - `UserActivatedIntegrationEvent`
   - `CustomerGoLiveIntegrationEvent`
2. Confirm ownership per service:
   - Accounts orchestrates process state.
   - Notifications sends activation email and publishes delivery.
   - Identity emits user activation.
3. Freeze V1 decisions:
   - Auto-transition to `CustomerReady` after user activation.
   - No first-login wizard in MVP.

### Phase 1: Accounts Domain and Persistence Foundation

1. Create aggregate `CustomerActivationProcess` in Accounts Domain with dual state machine (`Status` + `Step`), retry, fail, and strict guards.
2. Add internal domain events for activation milestones and go-live trigger.
3. Create repository contract and implementation using onboarding repository patterns.
4. Add EF configuration and DbSet entries in write/read contexts.
5. Generate migration for activation table and indexes (`SubscriptionId`, `TenantId`, `CorrelationId`, `AdminUserId`).
6. Add unit tests for valid and invalid transitions and retry behavior.

### Phase 2: Accounts Application Layer and API

1. Add idempotent commands and handlers:
   - `StartCustomerActivationProcess`
   - `RetryCustomerActivationProcess`
   - `ResendActivationEmail`
2. Keep command handling semantics aligned with platform patterns:
   - Persist aggregate.
   - `SaveChangesAsync`.
   - `AddAndSaveEventAsync` through outbox when publishing integration events.
3. Add query models and handlers for activation detail/list views using read context.
4. Add backoffice activation endpoints (detail, retry, resend) reusing onboarding API conventions.
5. Add DI wiring and event bus subscriptions for incoming activation events.

### Phase 3: Epic 1 to Epic 2 Handoff in Accounts

1. Extend `ExternalUserProvisionedIntegrationEventHandler` so onboarding completion triggers activation start idempotently.
2. Preserve duplicate guards and correlation logging.
3. Add guard against duplicate activation process creation for same subscription/admin.
4. Add focused tests for automatic handoff and duplicate event replay.

### Phase 4: Notifications Integration

1. Add `ActivationEmailRequestedIntegrationEvent` handler in Notifications.
2. Implement activation email composition and sending with `preferredLanguage` fallback policy.
3. Publish `ActivationDeliveredIntegrationEvent` through outbox only on successful send.
4. Add idempotency tests and failure-path tests (send failure, duplicate event).
5. Register event subscription and event type assembly in Notifications outbox configuration.

### Phase 5: Identity Activation Event Integration

1. Implement emission of `UserActivatedIntegrationEvent` when activation flow completes in Identity.
2. Ensure event publishing uses outbox and remains idempotent.
3. In Accounts, add `UserActivatedIntegrationEvent` handler to advance the process:
   - `MarkUserActivated`
   - `MarkCustomerReady`
   - `Complete`
   - Publish `CustomerGoLiveIntegrationEvent`
4. Add user mismatch and invalid-state guard tests.

### Phase 6: End-to-End Completion and API Integration Tests

1. Add functional tests for complete flow:
   - Onboarding completed.
   - Activation email requested.
   - Delivery confirmed.
   - User activated.
   - Customer go-live achieved.
2. Add retry/resend functional tests and duplicate-request replay tests (`x-requestid` idempotency).
3. Add authorization tests for activation endpoints based on existing onboarding policy style.

### Phase 7: Hardening Increment

1. Add observability:
   - Structured logs with `CorrelationId` in all new handlers and commands.
   - Activation funnel metrics.
2. Add operational safeguards:
   - Resend cooldown and max attempts.
   - Explicit activation error taxonomy.
3. Add timeout and recovery behavior for prolonged waiting states and dead-letter visibility.
4. Execute full cross-service regression and performance sanity checks.

## Dependencies and Parallelism

1. Sequential chain: Phase 1 -> Phase 2 -> Phase 3.
2. Parallel after contract freeze: Phase 4 and Phase 5.
3. Sequential completion: Phase 6 after Phases 3, 4, and 5.
4. Hardening (Phase 7) starts after MVP validation.

## Verification Strategy

1. Build baseline and ensure no compilation regressions.
2. Run unit tests for Accounts Domain/Application/Infrastructure:
   - Activation state machine.
   - Guard validations.
   - Idempotent command behavior.
3. Run unit tests for Notifications and Identity handlers:
   - Delivery/publish flow.
   - Outbox usage.
4. Run functional tests for Accounts activation APIs:
   - Detail, retry, resend endpoints.
   - Authorization.
   - Idempotent duplicate semantics.
5. Validate integration flow:
   - Onboarding completion triggers activation process.
   - Cross-service events conclude in `CustomerGoLive`.
6. Run regression checks ensuring existing onboarding tests still pass.

## Open Decisions for Refinement

1. Decide if resend cooldown is mandatory in MVP or only in Hardening.
2. Decide if activation list endpoint is mandatory in MVP or can be deferred after detail endpoint.
3. Decide if go-live should immediately activate subscription aggregate state or remain event-only in MVP.

# 1. Criterio de modelado

Para este caso, separaría la responsabilidad así:

### **Account Service**

Responsable del modelo de negocio de cuentas B2B:

- subscriptions
- tenants
- companies
- memberships de usuarios respecto a companies/tenants
- proceso de onboarding del customer

### **Identity Service**

Responsable de identidad y acceso:

- credenciales
- autenticación
- autorización
- roles/permisos
- clients / APIs
- usuarios internos y externos como identidades del sistema

### **Notifications Service**

Responsable de:

- envío de emails
- plantillas
- comunicaciones transaccionales derivadas de eventos

# 2. Glosario en inglés

Te propongo este glosario base. Es importante fijarlo pronto porque evita mucha ambigüedad en código, eventos, tablas y conversaciones técnicas.

## Core business terms

- **Subscription**: contractual entitlement that grants access to the platform under a specific plan.
- **Subscription Plan**: catalog definition of features, limits and rules available for a subscription.
- **Tenant**: logical isolation boundary that groups one or more companies under the same customer space.
- **Company**: legal or operational business entity inside a tenant.
- **Owner Company**: the primary company that owns the subscription.
- **Admin User**: initial external user with the highest permissions allowed by the subscription.
- **Internal User**: QLT System employee using the backoffice or internal tools.
- **External User**: customer-side user belonging to a tenant/company.
- **Membership**: link between a user and a tenant/company, including role assignment and status.
- **Onboarding**: process that initializes a new customer setup.
- **Backoffice**: internal operational application used by QLT System staff.
- **Sales Opportunity** or **Deal**: commercial sale input that originates the onboarding.
- **Project Manager**: internal role responsible for initializing and configuring the customer account.

## Identity and access terms

- **Identity User**: authenticated subject stored in Identity.
- **Role**: authorization grouping.
- **Permission**: granular authorization capability.
- **Client Application**: application or API registered in Identity.
- **Activation**: process through which a user sets credentials and gains access.
- **Invitation**: communication sent to enable initial login.

# 4. Modelo de dominio propuesto

## 4.1 Account Service

Aquí está el núcleo de la primera épica.

---

## **Aggregate: Tenant**

### Purpose

Representa el boundary organizativo del customer.

### Suggested fields

- `TenantId`
- `Name`
- `Status` (`Pending`, `Active`, `Suspended`, `Closed`)
- `OwnerCompanyId`
- `CreatedAtUtc`
- `CreatedByInternalUserId`
- `ActivatedAtUtc`
- `Version`

### Rules

- Un tenant puede contener múltiples companies.
- Un tenant debe tener exactamente una **Owner Company**.
- Un tenant nace durante el onboarding de una subscription.

---

## **Aggregate: Company**

### Purpose

Entidad empresarial dentro del tenant.

### Suggested fields

- `CompanyId`
- `TenantId`
- `LegalName`
- `TradeName`
- `CompanyType` (`Owner`, `Affiliate`, `Branch`, `Partner`)
Para la épica 1 bastaría con `Owner`.
- `TaxId`
- `CountryCode`
- `Status` (`Pending`, `Active`, `Inactive`)
- `CreatedAtUtc`

### Rules

- Toda company pertenece a un tenant.
- La primera company del tenant debe ser la **Owner Company**.
- La subscription queda asociada a la Owner Company.

---

## **Aggregate: Subscription**

### Purpose

Representa el derecho de uso contratado.

### Suggested fields

- `SubscriptionId`
- `TenantId`
- `OwnerCompanyId`
- `SubscriptionPlanCode`
- `Status` (`PendingInitialization`, `Active`, `Suspended`, `Cancelled`)
- `StartDateUtc`
- `EndDateUtc`
- `SeatsLimit` o límites de plan si procede
- `FeaturesJson` o snapshot del plan si queréis evitar dependencia fuerte externa
- `CreatedAtUtc`
- `CreatedByInternalUserId`

### Rules

- Una subscription pertenece a un tenant.
- Una subscription referencia una Owner Company.
- La activación de la subscription puede depender de completar onboarding.

---

## **Aggregate: UserMembership**

Aquí está una de las decisiones más importantes.

Yo **no metería el usuario como entidad de negocio dentro de Account** más allá de una referencia. El usuario como identidad vive en Identity. En Account modelamos su **vinculación al negocio**.

### Purpose

Representa la relación entre un usuario y la estructura de negocio.

### Suggested fields

- `MembershipId`
- `UserId` ← id del Identity service
- `TenantId`
- `CompanyId`
- `MembershipType` (`Internal`, `External`)
- `RoleCode` (`TenantAdmin`, `CompanyAdmin`, `CompanyUser`, etc.)
- `Status` (`PendingActivation`, `Active`, `Inactive`, `Revoked`)
- `IsPrimary`
- `CreatedAtUtc`

### Rules

- Un `UserId` puede tener múltiples memberships.
- Un external user debe pertenecer al menos a una company.
- El primer admin del customer debe crearse como membership en la Owner Company.
- Internal users normalmente no necesitarán `TenantId` ni `CompanyId` salvo que participen operativamente sobre tenants; si queréis separar bien, se puede tener dos submodelos, pero para simplificar puede admitirse nullable.

### Recomendación

Para evitar mezclar demasiado los dos mundos:

- **Internal users**: vivirán en Identity y podrán tener asignaciones de backoffice roles allí.
- **External users**: además de existir en Identity, tendrán `UserMembership` en Account.

Eso mantiene a Account centrado en el cliente B2B.

---

## **Aggregate: OnboardingProcess**

Yo sí modelaría este proceso explícitamente. En arquitecturas por eventos ayuda muchísimo a observabilidad y reintentos.

### Purpose

Orquesta y trazabilidad del alta inicial del customer.

### Suggested fields

- `OnboardingProcessId`
- `SubscriptionId`
- `TenantId`
- `OwnerCompanyId`
- `AdminUserId`
- `Status` (`Draft`, `InProgress`, `Completed`, `Failed`, `PartiallyCompleted`)
- `CurrentStep`
- `ErrorCode`
- `ErrorMessage`
- `StartedAtUtc`
- `CompletedAtUtc`
- `InitiatedByInternalUserId`

### Steps suggested

- `SubscriptionCreated`
- `TenantCreated`
- `OwnerCompanyCreated`
- `AdminUserProvisioned`
- `AdminMembershipCreated`
- `ActivationNotificationRequested`
- `Completed`

### Rules

- Debe existir un único onboarding process activo por subscription.
- Debe soportar idempotencia y reanudación.

### Purpose

Representa la identidad autenticable del sistema.

### Suggested business extensions

- `UserId`
- `Email`
- `FirstName`
- `LastName`
- `DisplayName`
- `UserType` (`Internal`, `External`)
- `Status` (`PendingActivation`, `Active`, `Locked`, `Disabled`)
- `PreferredLanguage`
- `CreatedAtUtc`

### Important note

Aunque Duende tenga su propio modelo y ASP.NET Identity el suyo, conceptualmente para vuestro dominio os interesa fijar esta abstracción.

---

## **Role model**

Distinguiría dos planos:

### **Platform roles** en Identity

Para acceso a backoffice y APIs:

- `SalesRepresentative`
- `ProjectManager`
- `BusinessAdmin`
- `SupportAgent`
- `PlatformAdmin`

### **Tenant roles**

Para customer-side authorization:

- `TenantAdmin`
- `CompanyAdmin`
- `CompanyManager`
- `CompanyUser`

Mi recomendación:

- Las **claims/roles técnicas** que usan las APIs y el backoffice viven en Identity.
- La **asignación contextual a tenant/company** vive en Account mediante `UserMembership`.

Identity puede emitir claims globales y, cuando haga falta contexto tenant/company, las APIs de negocio resuelven membresías desde Account.

Eso suele escalar mejor que meter toda la semántica multi-tenant dentro del token.

# 5. Internal users vs external users

Esto es clave y conviene dejarlo cristalino.

## **Internal users**

Usuarios de QLT System:

- sales representatives
- project managers
- business users
- support users
- platform admins

### Dónde viven

- **Identity** como `IdentityUser` con `UserType = Internal`
- autorización en Identity
- normalmente sin membership en companies del customer

## **External users**

Usuarios del cliente:

- admin user inicial
- futuros usuarios del tenant/company

### Dónde viven

- **Identity** como `IdentityUser` con `UserType = External`
- **Account** como `UserMembership` respecto a tenant/company

# 6. Relaciones clave del modelo

En términos conceptuales:

- **Subscription** belongs to **Tenant**
- **Tenant** contains one or more **Companies**
- **Owner Company** owns the **Subscription**
- **IdentityUser** may have zero or more **UserMemberships**
- **UserMembership** links **IdentityUser** to **Tenant** and **Company**
- **OnboardingProcess** coordinates the initial provisioning flow

Representación textual:

```
Tenant 1 --- N Company
Tenant 1 --- N UserMembership
Company 1 --- N UserMembership
Tenant 1 --- 1..N Subscription?
```

Aquí hay una decisión de negocio importante:

## ¿Un tenant puede tener más de una subscription?

Para esta primera épica yo te recomiendo:

- **v1 simple**: `Tenant 1 --- 1 Subscription`
- dejar preparado el diseño para evolucionar a `Tenant 1 --- N Subscriptions` si en el futuro necesitáis módulos/planes paralelos

Si no tenéis un caso claro de múltiples subscriptions por tenant, no lo abráis aún.

# 8. Flujo recomendado de onboarding

Con lo que has contado, yo lo haría así:

## Step 1

Un **Project Manager** inicia onboarding desde Backoffice.

## Step 2

**Account** crea:

- `Subscription`
- `Tenant`
- `OwnerCompany`
- `OnboardingProcess`

## Step 3

**Account** publica `CustomerAdminProvisioningRequestedIntegrationEvent` con:

- admin email
- first name
- last name
- user type = external
- tenant/company context mínimo de referencia

## Step 4

**Identity** crea el `IdentityUser` y publica `UserProvisionedIntegrationEvent`.

## Step 5

**Account** consume el evento y crea `UserMembership` con role `TenantAdmin` o `CompanyAdmin` según decidáis.

## Step 6

**Identity`o`Account`, según vuestro reparto**, solicita a Notifications el email de activación.

Mi recomendación:

- **Identity** debería ser quien publique el evento de activación/invitación, porque conoce el estado real de la identidad.
- **Notifications** envía el email.

## Step 7

Cuando todo está completo, **Account** marca `OnboardingProcess = Completed`.

# 9. Aggregate boundaries y consistencia

Aquí conviene ser estricto.

## Consistencia fuerte dentro de cada servicio

Dentro de **Account**:

- crear `Subscription`, `Tenant`, `OwnerCompany` y `OnboardingProcess` puede ser transaccional en Azure SQL si lo hacéis dentro del mismo bounded context.

Dentro de **Identity**:

- crear `IdentityUser` y su configuración inicial también transaccional.

## Consistencia eventual entre servicios

Entre `Account` e `Identity`:

- por eventos
- con patrón **Outbox**
- consumidores idempotentes
- correlation id / causation id

Esto es especialmente importante en onboarding.

# 11. Reglas de negocio iniciales

Estas reglas conviene dejarlas explícitas ya.

## Subscription rules

- A subscription cannot be activated without an owner company.
- A subscription cannot be activated without an admin user being provisioned.
- Only internal users with the proper backoffice role can initiate onboarding.

## Tenant rules

- A tenant must have exactly one owner company.
- A tenant can contain multiple companies.
- A tenant cannot be deleted while active subscriptions exist.

## Company rules

- The first company in a tenant must be the owner company.
- An owner company must belong to the same tenant as the subscription.

## User rules

- Every external admin user must exist in Identity before membership is created in Account.
- An admin user must have at least one active membership.
- Internal users cannot be assigned as customer admin users.

## Onboarding rules

- Onboarding must be idempotent.
- A failed onboarding can be retried safely.
- Duplicate provisioning requests must not create duplicate users or memberships.

- `SubscriptionPlan`
- `UserMembership`
- `OnboardingProcess`
- `InternalUser`
- `ExternalUser`
- `AdminUser`

## Avoid

- `CustomerAccount` si ya existe `Account Service`, porque puede generar colisión semántica
- `Organization` si negocio ya habla de `Company`
- `Client` para empresa compradora, porque en Identity/API `client` suele significar OAuth/OpenID client
- `UserCompanyRelation`, mejor `UserMembership`

# 15. Mi recomendación arquitectónica más importante

La decisión más importante aquí es esta:

## **Identity owns authentication and global authorization**

## **Account owns business context and tenant/company membership**

Si se intenta meter el modelo multi-tenant completo dentro de Identity, probablemente hay riesgo de mezclar y degradar el diseño con el tiempo.:

- autenticación
- autorización técnica
- jerarquía empresarial
- ownership de la subscription

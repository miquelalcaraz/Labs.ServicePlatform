## User Story 1 — Crear una nueva suscripción desde Backoffice

**Como** Project Manager de QLT System,

**quiero** registrar una nueva suscripción para un cliente desde el Backoffice,

**para** iniciar su alta en la plataforma B2B tras el cierre de una venta.

### Descripción

El Project Manager debe poder dar de alta una suscripción indicando, como mínimo, los datos básicos del cliente y el tipo o nivel de suscripción contratado.

### Criterios de aceptación

- El Project Manager puede acceder a una pantalla o formulario de creación de suscripción.
- El formulario solicita los datos mínimos necesarios para iniciar el alta.
- La suscripción queda registrada con un estado inicial definido.
- La suscripción queda vinculada al proceso de onboarding del cliente.
- El sistema informa si la creación se ha realizado correctamente o si existe algún error de validación.

---

## User Story 2 — Crear el tenant asociado a la suscripción

**Como** sistema,

**quiero** crear automáticamente un tenant al inicializar una nueva suscripción,

**para** proporcionar un entorno aislado y escalable al nuevo cliente.

### Descripción

Una vez creada la suscripción, el sistema debe generar un tenant único que actuará como contenedor lógico de la empresa compradora y de futuras empresas relacionadas.

### Criterios de aceptación

- Al inicializar una suscripción válida, se crea un tenant único.
- El tenant queda asociado a la suscripción creada.
- El tenant se genera con un identificador único dentro de la plataforma.
- No se permite crear dos tenants para la misma inicialización si el proceso ya se completó.
- El sistema registra el resultado del proceso de creación.

---

## User Story 3 — Crear la empresa propietaria de la suscripción

**Como** sistema,

**quiero** crear una empresa principal dentro del tenant,

**para** representar a la empresa compradora como titular de la suscripción.

### Descripción

El tenant debe contener una primera empresa obligatoria, que será la propietaria de la suscripción y la entidad principal del cliente dentro de la plataforma.

### Criterios de aceptación

- Al inicializar el cliente, se crea una empresa principal dentro del tenant.
- La empresa queda marcada como propietaria de la suscripción.
- La empresa queda vinculada al tenant recién creado.
- La suscripción queda asociada a esta empresa propietaria.
- La empresa se crea con los datos identificativos básicos definidos para el cliente.

## User Story 4 — Crear el usuario administrador inicial del cliente

**Como** Project Manager,

**quiero** registrar un usuario administrador para la empresa compradora,

**para** que el cliente disponga de un acceso inicial con los máximos permisos permitidos.

### Descripción

Durante el alta, debe crearse un usuario administrador perteneciente a la empresa principal. Este usuario será el primer responsable del lado del cliente y tendrá el mayor nivel de permisos posible según la suscripción contratada.

### Criterios de aceptación

- Se puede informar el nombre, apellidos, email y datos mínimos del administrador.
- El sistema valida que el email tenga formato correcto y no entre en conflicto con reglas de negocio definidas.
- El usuario administrador queda asociado a la empresa propietaria.
- El usuario administrador queda asociado indirectamente al tenant a través de su empresa.
- El usuario recibe el rol de mayor privilegio permitido para su tipo de suscripción.
- El usuario queda preparado para acceder a la plataforma mediante el mecanismo de activación definido.

## User Story 5 — Vincular correctamente suscripción, tenant, empresa y usuario

**Como** sistema,

**quiero** establecer las relaciones correctas entre las entidades creadas,

**para** garantizar la coherencia del modelo de datos desde el inicio del cliente.

### Descripción

La inicialización no consiste solo en crear registros, sino en dejar correctamente estructuradas las relaciones entre suscripción, tenant, empresa propietaria y usuario administrador.

### Criterios de aceptación

- La suscripción queda asociada a un único tenant.
- El tenant contiene al menos una empresa activa en el momento de su creación.
- La empresa principal queda identificada como titular de la suscripción.
- El usuario administrador queda asociado a la empresa principal.
- Todas las relaciones son consultables desde Backoffice.
- No puede completarse el onboarding si falta alguna relación obligatoria.

## User Story 6 — Ejecutar el alta inicial como proceso único de onboarding

**Como** Project Manager,

**quiero** ejecutar el alta inicial del cliente como un flujo único y controlado,

**para** evitar errores manuales y asegurar que la estructura base se crea de forma consistente.

### Descripción

Desde Backoffice, el Project Manager debe poder lanzar un flujo de inicialización que agrupe la creación de la suscripción, el tenant, la empresa principal y el usuario administrador.

### Criterios de aceptación

- El Backoffice ofrece una acción clara para iniciar el onboarding.
- El flujo presenta los pasos o datos necesarios de forma ordenada.
- El sistema confirma al finalizar qué entidades han sido creadas.
- Si una parte crítica del proceso falla, el sistema informa del fallo de forma comprensible.
- El estado del onboarding queda registrado.
- El Project Manager puede consultar posteriormente el resultado del proceso.

---

## User Story 7 — Validar datos obligatorios antes de completar la inicialización

**Como** Project Manager,

**quiero** que el sistema valide los datos obligatorios antes de crear la estructura del cliente,

**para** evitar altas incompletas o inconsistentes.

### Descripción

Antes de ejecutar el alta, el sistema debe validar que están presentes los datos mínimos requeridos para la suscripción, la empresa y el usuario administrador.

### Criterios de aceptación

- No se puede completar el proceso si faltan datos obligatorios.
- El sistema muestra mensajes de error claros por campo o bloque funcional.
- Las validaciones se ejecutan antes de la creación definitiva.
- El Project Manager puede corregir la información y reintentar el proceso.
- Solo se permite continuar cuando la información mínima es válida.

## User Story 8 — Consultar desde Backoffice el resumen del cliente inicializado

**Como** Project Manager,

**quiero** visualizar el resultado del alta del cliente en Backoffice,

**para** confirmar que la suscripción y la estructura base se han creado correctamente.

### Descripción

Tras la inicialización, el Backoffice debe mostrar una vista resumen con las entidades principales creadas y su estado.

### Criterios de aceptación

- El Project Manager puede ver la suscripción creada.
- Puede ver el tenant asociado.
- Puede ver la empresa principal creada.
- Puede ver el usuario administrador asociado.
- El sistema muestra el estado general del onboarding.
- La información es accesible sin necesidad de revisar logs técnicos.

## User Story 9 — Preparar el tenant para futuras empresas relacionadas

**Como** negocio,

**quiero** que el tenant quede preparado para albergar otras empresas relacionadas en el futuro,

**para** soportar la evolución natural del cliente dentro del modelo B2B.

### Descripción

Aunque en esta primera épica solo se crea una empresa inicial, la estructura debe quedar preparada para permitir que en el futuro se incorporen nuevas empresas dentro del mismo tenant.

### Criterios de aceptación

- El tenant no se diseña como una estructura de empresa única cerrada.
- La empresa inicial queda registrada como primera empresa del tenant.
- El modelo soporta la incorporación posterior de nuevas empresas relacionadas.
- La empresa propietaria queda distinguida frente a futuras empresas secundarias.
